# E7 测试代码重构评估报告

评估日期：2026-11-01。

2026-11-08 接续：以下保留原评估时的现象与建议。后续 v2 已统一运行管理与结果，P1 已完成 SoC 逐条 DiffTest、总线监视扩展和完整 128 MiB 比较优化。现行接口见 [测试库说明](npc/tests/README.md)，实际验收见学习记录 §51。

正式源码：WSL Ubuntu-22.04，`/home/ysyx/ysyx-workbench`。Windows 副本：`E:\ysyx\e\e7`。

本报告根据当前源码和现有学习记录评估测试结构，说明优点、缺点、改进策略和改进原因。本次没有重构正式源码，没有编译或运行测试；本文中的建议不代表已经实现。历史验证与本次源码同步分别说明。

## 1. 评估结论

现有体系已经具备通用检查、CPU 状态观察、仿真驱动、手写期望、逐指令 DiffTest、批量调度和波形检查。适合保留这些基础，在它们之间统一运行结果、配置和错误报告。

优先解决四件事：

1. 明确区分正常结束、预期非法指令、超时和仿真故障。
2. 让多个 runner 使用一致的运行配置和结果格式。
3. 复用已有差异收集器，减少重复判断与统计。
4. 将 SoC 的人工观察结果和自动验收结果分开。

当前不建议整体更换框架，也不建议为了统一而将独立 NPC 和 SoC 的存储器模型合并。

## 3. 现有优点及应保留的设计

| 优点 | 为什么有价值 | 重构时如何处理 |
|---|---|---|
| 普通入口、手写期望、DiffTest 分工明确 | AM 的 a0=0 约定不适用于所有手写程序；不同证据可以交叉核对 | 保留不同验收规则，只共享运行基础设施 |
| EXPECT 和汇编程序放在一起 | 修改案例时，指令和预期结果容易一起检查 | 保留现有格式，避免换格式导致全量迁移 |
| 参考模型与 NPC 的存储器独立 | 能发现 RTL 与参考执行结果的差异 | 保持独立状态，不让两边共享实际计算结果 |
| cpu_view.h 集中维护内部路径 | CPU 模块层级变化时，不必到每个 runner 修改生成名称 | 保留并明确区分独立 NPC 与 SoC 的观察实现 |
| 提交拍 DiffTest | 多周期等待不会让参考模型比 NPC 多执行指令 | 重构必须保持提交与拒绝时机的语义 |
| 固定及随机回复可配置 | NPC_MEM_DELAY 支持随机或固定 1～20 拍，无需改源码重编译 | 保留环境变量兼容，逐步纳入统一配置 |
| 通用检查库有自测 | 已考虑失败传播、零检查拒绝和多差异收集 | 继续用它验证检查器，不必另建测试框架 |
| 保留逐指令比较、末态期望和波形 | 最终结果和中间时序覆盖不同问题 | 不因为 DiffTest 通过就删掉协议或波形检查 |
| 多个 Makefile 复用已有规则 | cpptest、diff、wave 已有共用基础 | 优先保持命令兼容，不让重构迫使上层 AM 同时修改 |

## 4. 问题、改进策略和原因

### 4.1 运行结果语义不够明确——优先级 P1

**现状与不足：** `sim_step()` 返回 bool。false 可以表示非法指令、取指不对齐等情况；true 也包括已经结束时的提前返回。调用方还要查询其他标志和打印信息，才能知道原因。

**改进策略：** 引入明确的运行状态，例如继续、正常 ebreak、非法指令、非法访问、周期超时、指令数超时、内部错误。结果携带出错 PC、指令和原因。仿真层只报告事件，由测试策略判断事件是否符合预期。

**为什么改：** 同一个非法指令事件，在普通程序中是失败，在 boundary 测试中可能是正确结果。明确状态能避免多入口各自猜测、重复分支和丢失诊断信息。

**边界：** 这里是接口可维护性问题，不能只凭一条分支推断当前非法指令测试已经失败。现有学习记录已有边界回归通过的结果，本次未复测。

### 4.2 多个 runner 重复管理生命周期——优先级 P1

**现状与不足：** main.cpp、cpu_test.cpp、difftest.cpp 都负责初始化、复位、循环、预算判断、关闭波形和输出。多处提前 return 需要手动调用 sim_close。

**改进策略：** 提取一次仿真运行的基础管理：初始化、复位、按周期推进、预算检查、资源关闭。逐周期运行与运行到提交/拒绝事件分别提供明确接口。保留 AM、EXPECT、DiffTest 三种上层判断规则。先用普通结构体和函数完成，不急于引入继承和插件系统。

**为什么改：** 修改复位、超时或波形行为时只需维护一处；在失败路径也能关闭波形。不同测试仍保留自己的成功标准。

**约束：** 不改变原来上升沿前采样、沿后回复的顺序，不增加额外周期，不把 SoC 的复位要求直接套到独立 NPC。

### 4.3 DiffTest 重复实现比较与统计——优先级 P2

**现状与不足：** check.h 已有 DiffCollector，但 difftest.cpp 仍用本地 Counts 配合 Difference 数组。计数、差异收集和报告存在两套近似实现。

**改进策略：** 复用差异收集能力，分别保留架构状态、辅助检查和内存检查三组统计；将一次指令比较与整轮累计统计分开。

**为什么改：** 错误格式和字段比较能统一，减少后续加字段时的重复修改。

**注意：** DiffCollector.clear() 当前会清空计数，不能直接用它替换全部累计统计；否则每步 17 项和整轮汇总可能改变。普通 Checker 与逐指令 DiffCollector 用途不同，不必合成一个大类。

### 4.4 配置、全局状态和计数口径分散——优先级 P1

**现状与不足：** sim.cpp 用多个 static 变量保存请求、周期、提交数、LFSR 和波形对象。main 的周期上限、cpu_test 的 64000 周期、DiffTest 的指令/周期预算，以及 Python 的 15/20 秒限制分散在不同文件。

**改进策略：** 用 SimConfig 描述固定延迟、随机种子、预算、日志与波形；用 SimState 保存运行状态，集中完成重置。区分 clock_cycles、retired_instructions、attempted_instructions、wall_timeout。保留 NPC_MEM_DELAY 作为现有调用的兼容入口。

**为什么改：** 可复现测试需要同时知道程序和配置。仿真周期与真实秒数含义不同，机器负载变高不能被误判为 CPU 死循环。

**注意：** 不改 RTL 的复位规格，也不依靠悄悄清空 GPR 来掩盖未初始化读取。测试初始化策略要明确记录。

### 4.5 机器结果与人读日志混合——优先级 P2

**现状与不足：** run_cpu_tests.py 用退出码判断成功，但还解析 PASS 文本生成摘要；run_acceptance.py 会解析 EMU 的 step、a0 和 ebreak 文本来判定结果。调整输出格式可能破坏调度脚本。

**改进策略：** 输出统一的结构化结果，至少含案例、后端、停止原因、成功与否、周期/提交数、检查数、失败数、配置及日志路径。人读日志继续保留。统一捕获子进程超时、启动失败和信号退出，单案例失败后继续运行其他案例。

**为什么改：** 判断不再依赖日志排版，失败可以准确归类。当前 run_acceptance.py 没有与 run_cpu_tests.py 等价的异常处理，子进程超时会中断整批运行。

### 4.6 波形案例检查不等于通用协议检查——优先级 P2

**现状与不足：** 当前脚本检查固定 PC、固定程序和固定内部信号，适合证明这些案例的 add/lw/sb 行为。它并没有自动遍历每笔请求，证明任意等待期间都无提前提交、重复发送或错误写回。

**改进策略：** 保留现有案例检查，再利用仿真中已有的请求记录补通用协议监视：记录任务接受、请求发送、回复和提交；检查一笔任务不重复发送、无请求不能回复、未完成不能提交、等待期间 PC/GPR 不发生违规更新。请求拍检查总线字段，完成拍检查提交与写回。

**为什么改：** 最终状态正确不能证明中间拍合法，历史提前写回实验已经说明两者覆盖面不同。

**注意：** 请求被接受后 CPU 总线端口是否还必须保持，由协议约定决定；不要凭监视器臆造额外的保持要求。跨周期任务对应关系应使用已保存的字段。

### 4.7 SoC 当前缺少自动成功标准——优先级 P1

**现状与不足：** soc_main.cpp 已有 Flash 镜像加载和读取；目前镜像路径写死，运行到观察上限时返回 0，同时提示人工检查 hello 串口输出。SoC 没有接入逐指令 DiffTest。

**改进策略：** 将镜像路径和观察预算参数化；明确观察结束、自动通过和失败三种结果。Flash 通路测试、提供的 hello 输出观察、可退出的 dummy 测试分别设定适合的验收条件。需要自动检查串口时，优先比较语义输出，不把全部日志逐字节锁死。

**为什么改：** 运行到上限只表示仿真进行了若干周期，不能作为 hello 成功的证据。后续批量测试必须有能自动判断的条件。

**注意：** 提供的 hello 本来可能持续循环，不应一律要求 ebreak 或把所有观察上限都算 CPU 故障。独立 NPC 的观察层不能直接用于 VSimTop，需要另行核对层级与接线。

### 4.8 全内存比较与失败输出的规模——优先级 P3

**现状与不足：** 每个 DiffTest 程序结束都比较 128 MiB，共 33554432 个字。强检查覆盖完整，但对很短的程序有固定成本；若大量字不同，逐项收集差异还可能占用大量内存。

**改进策略：** 先只限制打印与保存的差异数量，同时继续统计全部错误。测量全内存检查的耗时后，再决定是否提供快速模式；若只比较写过的页，需要分别记录 NPC 和 EMU 的写集合并比较并集。正式验收仍保留全内存模式。

**为什么改：** 控制故障时的输出规模比盲目删检查更稳妥。性能优化应由测量支撑，并保留可以发现意外写入的强验证模式。

## 5. 推荐实施顺序与验收

| 顺序 | 一次修改的范围 | 应验证的结果 |
|---|---|---|
| 1 | 统一停止状态、错误上下文和预算配置 | 正常结束、预期非法、真实故障和超时可区分，案例判断不变 |
| 2 | 收拢生命周期和资源关闭 | main/cpu_test/difftest 公共行为一致，波形正常关闭，周期与提交数不变 |
| 3 | DiffTest 复用比较器 | 每步架构检查、辅助检查、内存检查和故障定位信息保留 |
| 4 | 统一结构化结果与 Python 异常处理 | 修改人读日志不影响通过判断；单例超时不终止其余案例 |
| 5 | 补协议监视器 | 通过一笔 store 和一笔 load 的具体请求/回复/提交过程确认检查口径；用已有故障材料核对检出能力 |
| 6 | SoC 验收参数化 | 通路、观察和程序通过分别报告，不把达到上限当成功 |
| 7 | 有测量依据后优化内存检查 | 快速模式和完整模式有清晰边界，正式强验收保留 |

每次重构只改一层，保留原有命令。优先使用现有 test-library、默认/固定一拍手写测试、DiffTest、三方验收和波形入口。代码和行为稳定后，再根据影响补完整 AM cpu-tests、RV32I；不因整理报告或复制源码重跑长时间 archbench。

新建或变更构建、测试入口时再更新 `e/测试与构建入口索引.md`；实际结果仍写 `E7学习记录.md`。本报告是结构评估，不替代验收记录。
