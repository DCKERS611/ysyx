## 一、阶段 A：把 AM 和红白机跑起来

### 1. 先确认原文怎么走

E6 讲义只说“按 PA1 的《NEMU 是什么?》跑红白机”，没给具体命令；PA1 原文又默认 fceux-am 在 PA0 已经 clone 过。我们的 workbench 不是 ics2025，先看了 `~/ysyx-workbench/init.sh`：`bash init.sh abstract-machine` 会 clone abstract-machine（ics2026，并把 `AM_HOME` 写进 `.bashrc`），顺带 clone fceux-am（ics2021）。所以不用另外找 fceux 的源码和构建方式。

fceux-am 的 README 约定：ROM 放在 `nes/rom/xxx.nes`，用 `make ARCH=native run mainargs=xxx` 运行，`mainargs` 就是 ROM 文件名（不含扩展名）。键位：U/I 是 SELECT/START，J/K 是 A/B，WASD 是方向，Q 退出。

## 二、这一阶段弄明白的事

1. 红白机游戏本身就是一条条 6502 指令。fceux 是运行在 Linux 上的普通程序，用软件逐条解释 6502 指令、模拟 NES 的硬件，游戏分不清自己跑在真机还是模拟器上。这和 minirvEMU 解释 minirv 指令是同一类做法。
2. AM 用 `ARCH` 选平台：同一份源码，`ARCH=native` 编到 Linux 上直接跑；后面编 `ARCH=minirv-npc` 时会生成 minirv 指令序列，链接到我们自己的运行时，最后跑在 NPC 上。
3. `mainargs` 是程序自己的参数：fceux 用它选 ROM（ROM 在构建时被编进二进制），cpu-tests 用它选测例，am-tests 用它选测项（`k` 键盘、`t` 时钟）。

## 三、注意点

- PA1 的命令是按 ics2025 目录写的，直接照抄会找不到 `ics2025`；在 ysyx-workbench 里正确做法是用 `init.sh` 的子项目名。
- ROM 文件名就是 `mainargs` 的值，改名后要同步改参数。
- 导弹防线初始界面不放声音，进关卡才有，这是游戏本身的行为，不是环境问题。
- 按键输出如果和实际按键不符，先切英文输入法（中文输入法兼容问题）。

### 2. 编到 minirv

`make ARCH=minirv-npc ALL=dummy` 同样出了三个文件。读反汇编：

| 地址 | 内容 | 作用 |
|---|---|---|
| `0x80000000` | `li s0,0` | `_start` |
| `0x80000004` | `lui sp,0x80009` | 设栈 |
| `0x8000000c`–`0x80000014` | `lui ra` / `addi` / `jalr` | 跳到 `_trm_init`（0x80000020） |
| `0x80000018` | `li a0,0` / `ret` | `main` |
| `0x80000020`–`0x80000038` | 压栈、设参、`jalr` | `_trm_init` 调 main |
| `0x8000003c`–`0x80000044` | `lui tp` / `addi tp,tp,60` / `jr tp` | 跳到 0x8000003c 自身：halt 的 `while(1)` |

整段只有 `addi/lui/jalr/sw` 四种指令，都在 minirv 的 8 条之内。

### 3. NPC 改造

改了四处：

- `ifu.v`：`Reg #(32, 32'h0)` 改成 `Reg #(32, 32'h80000000)`，复位后 pc 从 0x80000000 开始。
- `pmem.cpp`：`M[256]` 改成 `M[32*1024*1024]`（128MB）。
- `pmem.cpp` 装载：删掉了 `uint8_t bytes[sizeof(M)]` 和 `uint32_t words[...]` 两个大数组（改大后它们是栈上的 128MB，会爆栈），改成 `memset` 后 `fread((uint8_t*)M, 1, byte_count, file)`，直接按字节落进存储器。x86 和 RISC-V 都小端，不转换。
- `pmem_read` / `pmem_write`：地址先减 `0x80000000` 再除以 4，边界判断也改用偏移。

编译时踩了两个小坑：`std::memset` 缺 `#include <cstring>`；`fread` 一开始还读进已删除的 `bytes`，并且把旧的“逐字节拼字”循环留在了下面，整段删干净才对。

第一版只改了大数组和 fread、读写仍按绝对地址索引，运行时在 `pc=0x80000010` 报 `pmem_read out of range`——`0x80000010` 是取的地址本身，不是偏移。改成先减基址后解决。

### 4. 跑 dummy

```bash
make -f Makefile.cpptest run PROGRAM=../am-kernels/tests/cpu-tests/build/dummy-minirv-npc.bin
```

日志里的 pc 依次 0x80000000→04→08→0c→10→14→跳到 20→…→38→跳到 18→1c→3c，之后在 `3c→40→44→3c` 循环，1000 拍超时。结束时 `a0=0`、`ra=0x8000003c`，没有 illegal。

### 2. 结束状态和自动运行（C2～C4，2026-10-21）

- `halt(code)` 改为 `asm volatile("mv a0, %0; ebreak" : : "r"(code));`。
- NPC 在运行结束后读取 a0；只有触发 ebreak 才输出 GOOD/BAD TRAP。TestSuite 同时检查 hit ebreak 和 a0==0，通过 `tests.report()` 返回进程结果。
- `npc.mk` 的 run 规则调用 `$(MAKE) -C /home/ysyx/ysyx-workbench/npc -f Makefile.cpptest run PROGRAM="$(IMAGE).bin"`，程序路径已由 NPC 命令行参数接收。
- 用户终端日志：dummy 镜像 144 字节，17 周期，halt_pc=0x80000040、a0=0，GOOD TRAP、PASS: 2 checks，外层 dummy PASS。
- 用户终端日志：wrong 同为 17 周期，a0=1，BAD TRAP、FAILED: 1/2，非零结果已传回 AM。后续 riscv-tests 全套运行进一步验证了自动运行入口。

踩坑：系统有 python3 不代表有 python，安装 python-is-python3 后 AM 的 insert-arg 可用。Makefile 的 `$(MAKE)` 和 `-C` 均区分大小写；误写为 `$(make) -c` 会展开为空变量，并使开头的减号被解释为忽略错误，导致假 PASS。PROGRAM 参数必须和命令写在同一行。

## 十一、阶段 E：设备（UART + 时钟，2026-10-24）

设备（MMIO）在仿真环境里的做法：一段地址不进存储器数组，而是在 `pmem_read` / `pmem_write` 里被认出来、返回或输出。处理器本身不知道区别，它照常发 load/store。所以每个设备都是两侧一起改：`npc/csrc/pmem.cpp` 管「地址被访问时给什么」，AM 侧（`trm.c` / `timer.c`）管「用哪条指令去访问」。

### 1. E1：串口数据寄存器 0x10000000

一条 `sb` 的路径：`putch` 编出 `lui` + `sb`，LSU 在 `posedge clk` 且 `mem_write` 时调用 `pmem_write(0x10000000, ch, 0x01)`。`pmem_write` 原来第一行就是 `addr = waddr - MEM_BASE`，`0x10000000 - 0x80000000` 变成 `0x90000000`，撞上越界检查 `abort`。所以在减法之前加分支：

```cpp
if (static_cast<uint32_t>(waddr) == 0x10000000u) {
    std::fputc(wdata & 0xff, stderr);
    return;
}
```

`putch`：

```c
void putch(char ch) {
    volatile char *tx = (volatile char *)0x10000000ul;
    *tx = ch;
}
```

输出走 `stderr` 而不是 `stdout`：stdout 还要留给 `HIT GOOD TRAP`、`PASS` 这些判定行，混在一起后 `make ... run 2>&1 >/dev/null` 这类只看正文的命令就没法用了。

EMU 侧同步改：`step()` 里判断访存地址是否落在 `0x10000000–0x10000fff` 或 `0x20000000–0x20000fff`，加 `device_store`，边界检查与 `case Op::sw/sb` 的写内存都用 `if (!device_store)` 跳过。这一版只放行 store，load 仍走原路径（E2 才处理）。

验证：

```bash
cd ~/ysyx-workbench/am-kernels/kernels/hello
make ARCH=minirv-npc run 2>&1 >/dev/null       # 只有正文
make ARCH=minirv-npc run DIFFTEST=1 2>&1 | tail -6
```

正文两行（`Hello, AbstractMachine!` / `mainargs = ''.`）；DiffTest 输出 `HIT GOOD TRAP: a0=0x00000000`、`[ DIFF PASS ]`、`PASS: 70414 (4142 steps x 17)`、`Memory: PASS 33554432 words`。

踩坑：

- `std::fputs(wdata & 0xff, stderr)` 编译报 `invalid conversion from 'int' to 'const char*'`。`fputs` 收字符串，`fputc` 收一个字符，差一个字母。
- `device_store` 第一次声明在 `if (load || store) { ... }` 的花括号里，后面的 `switch` 报 `'device_store' was not declared in this scope`。要挪到 `if` 外面先给默认值，内层只写赋值；内层若再写 `const bool` 就变成影子变量，编译能过、DiffTest 在第一条串口 store 上崩。
- 改完 `emu.cpp` 后 `vim` 没有保存，mtime 不变，make 不重编，链接的还是带注入的目标文件。判断方法不是删构建目录，而是看编译日志里有没有 `-c -o emu.o .../emu.cpp` 这一行。
- 注入「删掉 `putch` 的 `volatile`」**现象没有变化**，字符照样输出。原因是 GCC 不会对「通过指针写绝对地址」做死存储消除——它无法证明那块内存没有外部观察者，且 `putch` 是导出函数。这条注入对当前判据是盲的，不能反过来证明 `volatile` 多余；`volatile` 真正的可观测差别出现在 E2 的轮询循环里。

### 2. E2：状态寄存器 0x10000004 与轮询

`pmem_read` 在减 `MEM_BASE` 之前加：

```cpp
if (static_cast<uint32_t>(raddr) == 0x10000004u)
    return (std::rand() & 0x7) == 0 ? 1 : 0;
```

`rand() & 0x7` 是 0 的概率 1/8，即 12.5% 就绪。`putch` 改成先读状态、就绪再写：

```c
volatile char *tx = (volatile char *)0x10000000ul;
volatile int  *status = (volatile int *)0x10000004ul;
while ((*status & 1) == 0) { }
*tx = ch;
```

这里 `volatile` 是硬的：去掉后编译器在 `-O2` 下会把 `*status` 提到循环外只读一次，读到 0 就永远出不来。

DiffTest 新增「设备读以 NPC 为准」：

- `emu.h`：`StepInfo` 加 `device_load`、`device_load_rd`；`Emulator` 加 `set_reg(index, value)`（内部写 `state_.R[index]`，`index != 0` 才写）。
- `emu.cpp`：`device` / `device_store` / `device_load` 三个变量都声明在 `if (load || store)` 外；`device_load` 时 `Op::lw` / `Op::lbu` 返回占位 0，不碰内存；`if` 之后写 `info.device_load = device_load; info.device_load_rd = rd;`。
- `difftest.cpp`：`emu.step()` 和 `get_state()` 之后、第一组比较之前，把 NPC 的写回值抄给 EMU：

```cpp
if (info.device_load && info.device_load_rd != 0)
    emu.set_reg(info.device_load_rd,
                dut.rootp->top__DOT__u_rf__DOT__rf[info.device_load_rd]);
```

能直接用 `rf[rd]` 是因为 `sim_step` 已经跑完，load 的写回在这一拍发生。

验证：`make ARCH=minirv-npc run DIFFTEST=1`，正文正常，`[ DIFF PASS ]`，`PASS: 426139 (25067 steps x 17)`，`protocol/read checks: 184973`。步数从 4142 涨到 25067 是轮询的直接证据：每输出一个字符平均读 8 次状态。

踩坑：

- 设备分支第一次写成 `static_cast<uint32_t>(raddr) >= 0x10000000u`，把取指地址 `0x80000000` 也接住了。现象是第 1 步 `inst: actual=0x00000000`、`illegal=1`、`pc` 停在 `0x80000000`、`FAILED: 4/24`。必须用 `==` 精确匹配单个设备地址。
- `device_load` 同样第一次声明在 `if` 里。
- `info.device_store = device_store;` 编译报 `StepInfo has no member named 'device_store'`。设备写不需要报告给 DiffTest，删掉这一行。
- `difftest.cpp` 里把 `device_load_rd` 打成 `device_loa_rd`，编译失败。
- `Op::lbu` 最初漏改，只改了 `Op::lw`。hello 只用 `lw` 读状态所以没暴露，但设备字节读会越界。

### 3. E3：时钟 0x20000000 / 0x20000004

`pmem.cpp` 加（`#include <sys/time.h>`）：

```cpp
static uint64_t get_time()
{
    struct timeval tv;
    gettimeofday(&tv, nullptr);
    return static_cast<uint64_t>(tv.tv_sec) * 1000000ull + tv.tv_usec;
}
```

`pmem_read` 里：

```cpp
if (static_cast<uint32_t>(raddr) == 0x20000000u)
    return static_cast<int>(get_time() & 0xffffffffu);
if (static_cast<uint32_t>(raddr) == 0x20000004u)
    return static_cast<int>(get_time() >> 32);
```

AM 的 `timer.c`：

```c
void __am_timer_uptime(AM_TIMER_UPTIME_T *uptime) {
  uint32_t lo = *(volatile uint32_t *)0x20000000ul;
  uint32_t hi = *(volatile uint32_t *)0x20000004ul;
  uptime->us = ((uint64_t)hi << 32) | lo;
}
```

`(uint64_t)hi` 不能省：`hi` 是 32 位，直接左移 32 位会被移空。

DiffTest 一行没改——`device_load` 的区间已经覆盖 `0x2000xxxx`，抄值逻辑通用。

验证：

```bash
cd ~/ysyx-workbench/am-kernels/tests/am-tests
timeout 10 make ARCH=minirv-npc run mainargs=t 2>&1 >/dev/null | head -20
timeout 15 make ARCH=minirv-npc run DIFFTEST=1 mainargs=t 2>&1 | grep -E "FAILED|DIFF PASS|EMU fault"
```

看到 1～20 秒逐行递增；20 行在 10 秒内打完，说明 NPC 比真实时间快，而秒数与真实时间同步，`uptime` 来自宿主机 `gettimeofday` 而不是仿真周期——这正是 F4 要改的地方。DiffTest 那一轮跑满 1000 万步、连续输出 125 秒，没有一行不一致，最后 `DiffTest timed out after 10000000 steps`。这是上限触发，不是失败：死循环测试不可能出现 `[ DIFF PASS ]`，只能验证「全程一致」。

踩坑：两个时钟分支最初写在越界检查**之后**，`0x20000000` 被当成存储器地址，报 `pmem_read out of range: addr=0xa0000000`。打印的是减完 `MEM_BASE` 的值，反推真实地址 `0xa0000000 + 0x80000000 = 0x20000000`。规律：设备分支必须在进入存储器路径之前 `return`。

### 4. F4：把时间换成周期数

改两处。

`npc/csrc/sim.cpp`：`g_cycles` 放在**文件作用域**，`sim_cycles()` 不加 `static`（要给 `pmem.cpp` 用），`sim_init` 里清零，`sim_step` 末尾 `++g_cycles`：

```cpp
static uint64_t g_cycles = 0;
uint64_t sim_cycles() { return g_cycles; }
```

不能放在 `eval_step` 里计数：一次 `sim_step` 调用 `eval_step` **两次**（`clk=0` 一次、`clk=1` 一次），`sim_reset` 里还有三次，放那里一条指令会被算成 2 拍。

`npc/csrc/pmem.cpp`：

```cpp
#define NPC_FREQ_HZ 100000000ull

static uint64_t get_time()
{
    return sim_cycles() * 1000000ull / NPC_FREQ_HZ;
}
```

必须先乘后除，且 `1000000ull` 要带 `ull` 后缀。

实测（dhrystone，`NUMBER_OF_RUNS = 2000`）：

| 假设频率 | 周期数 | 计时区间 | 分数 |
|---|---:|---:|---:|
| 1000MHz | 9,944,140 | 9 ms | 391 Marks |
| 100MHz | 9,944,103 | 97 ms | 36 Marks |

周期数只差 37 拍（0.0004%，来自串口状态读的随机数），时间和分数反比于频率，比值约 10.8。coremark 同样：100MHz `Total time 349 ms`、1000MHz `35 ms`，拍数都是 3567 万左右。

比值是 10.8 而不是 10.0，原因是整数截断：真实耗时 9.944 ms 被截成 9、99.44 被截成 97（说明那一轮实际是 97.x），分母小的那组相对误差更大。要压到 1% 以内，迭代次数得加到 20000。

这一步踩了两个坑：

- **判据一开始定错了。** 以为 `Finished in N ms` 覆盖整个程序，用总拍数去除。实际上 `dry.c` 里 `Start_Timer()` 在 printf 之后、循环之前，`NUMBER_OF_RUNS=2` 时计时区间只有几千拍，`0 ms` 是正确的。换 coremark 的 `Total time`（包住两轮矩阵运算）才是有效判据。
- **archbench 一开始全部报 `1 us`。** 那时 `++g_cycles` 还没加上，`bench_uptime()` 恒返回 0，`bench.c` 里 `if (diff == 0) diff = 1;` 把 0 兜成 1。补上计数器后重跑，`000.hello` 变成 98 us、`202.llama2` 变成 510 ms，和拍数除以 100000 对得上。

## 十四、阶段 G 与 E6 收尾（2026-10-26）

### 1. 将取指、访存移到 CPU 外部
