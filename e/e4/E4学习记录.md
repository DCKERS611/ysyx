# E4 学习记录：处理器的仿真和验证

更新时间：2026-10-13
参考资料：[一生一芯 26.07 E4 讲义](https://ysyx.oscc.cc/docs/2607/e/4.html)、Verilator Manual、NVBoard 项目 README 与示例

## 一、学习目标

E4 的目标是从“写 C 程序”转到“写 RTL 电路”。核心是掌握一条完整链路：用 Verilog 描述电路，用 Verilator 把电路编译成可执行的 C++ 仿真程序，运行仿真、生成波形、并用 NVBoard 虚拟板卡做交互验证。

与 E3 最大的不同是引入了**结构化建模**这一约束：不用 `always` 行为建模，只用“实例化 + 连线”和 `assign` 描述电路。这是本阶段需要反复训练的技能。

我的 RTL 练习代码放在 WSL 的 `/home/ysyx/ysyx-workbench/npc`；Windows 文档放在 `E:\ysyx\e\e4`。

## 二、Verilator 仿真环境

### 1. 安装

从 git 安装 Verilator 的 stable 版本，安装在 `~/tools/verilator-stable`，**放在 `ysyx-workbench` 目录之外**——否则 git 会去追踪 Verilator 的源码，占用磁盘。

安装后确认：

```bash
which verilator        # /usr/local/bin/verilator
verilator --version    # Verilator 5.050 2026-07-01
```

### 2. 理解工作流

Verilator 不是解释器，它把 Verilog **翻译成 C++ 类**：`module top` 生成类 `Vtop`，模块的端口变成这个类的成员变量（`input a` → `top.a`，`output f` → `top.f`）。仿真程序就是操作这个类的实例：给成员赋值（喂输入）、调用 `eval()`（让电路重新计算）、读取成员（取输出）。

完整流程：

```text
vsrc/*.v + csrc/*.cpp  ──► Verilator ──► build/obj_dir/Vtop（可执行文件）──► 运行 ──► wave.fst
```

### 3. npc 项目结构

```text
npc/
├── Makefile          构建脚本（sim / wave / lint / clean 等规则）
├── .gitignore        白名单模式：只追踪源码，忽略 build/
├── csrc/main.cpp     仿真驱动
├── vsrc/*.v          RTL 源码
├── constr/*.nxdc     约束文件（NVBoard 引脚绑定用）
└── build/            编译产物（可随时删除重建）
```

`.gitignore` 用白名单写法（先忽略一切，再放行 `.v`、`.cpp`、`.h`、`Makefile` 等源码类文件），所以只有源码进版本库，`build/` 里的产物永远不进 git。

## 三、组合逻辑与波形

### 1. 双控开关

第一个电路是双控开关，两个输入异或后驱动一个输出：

```verilog
module top(
    input  a,
    input  b,
    output f
);
    assign f = a ^ b;
endmodule
```

`assign` 是数据流建模——把 `a` 和 `b` 的异或结果连到 `f`。

### 2. 仿真驱动 main.cpp

`main.cpp` 遍历 `a`、`b` 的全部四种组合，每次 `eval()` 后打印输出并用 `assert` 检查：

```cpp
for (int a = 0; a <= 1; a++) {
    for (int b = 0; b <= 1; b++) {
        top.a = a;
        top.b = b;
        top.eval();                          // 让电路重新计算
        std::printf("a=%d b=%d f=%d\n", a, b, (int)top.f);
        assert(top.f == (a ^ b));            // 自动检查
    }
}
```

我没有用参考实现的随机输入，而是穷举了四种组合——覆盖更完整。

### 3. 波形

用 `VerilatedFstC` 记录波形，输出到 `build/wave.fst`：

```cpp
VerilatedFstC trace;
top.trace(&trace, 99);
trace.open("build/wave.fst");
// 每次 eval 后：
trace.dump(context.time());
context.timeInc(1);      // 时间前进一格
```

用 GTKWave 打开 `wave.fst`。一开始看到信号的离散间距很大、以为没有变化，后来把光标在四个时间点移动、逐个读值，确认 `f` 依次是 `0 → 1 → 1 → 0`，与四种输入组合一致。

GTKWave 里的读法：左侧 Signals 面板是电路所有信号的清单，Waves 面板是你实际添加查看的信号；光标处的值显示为“信号名=当前值”。波形里 1 位信号高电平画在上方、低电平画在下方。

## 四、NVBoard 虚拟板卡

### 1. 安装与示例

NVBoard（NJU Virtual Board）是基于 SDL 的虚拟 FPGA 开发板，支持 LED、七段数码管、拨码开关、UART、键盘和 VGA。

```bash
cd ~/ysyx-workbench
bash init.sh nvboard
sudo apt install libsdl2-dev libsdl2-image-dev libsdl2-ttf-dev
```

环境变量 `NVBOARD_HOME` 需要自己写入 `.bashrc`（我一开始 `echo $NVBOARD_HOME` 为空，重载 shell 后正常）。

先运行官方示例确认环境：

```bash
cd ~/ysyx-workbench/nvboard/example
make run
```

窗口里能看到数码管、按键、LED（15~0）、开关（SW）、VGA 显示区域和 PS/2 键盘。

### 2. 工作原理

NVBoard 通过**把 Verilog 端口绑定到板子引脚**来工作，涉及三个东西：

```text
① 约束文件 .nxdc        （手写：端口 → 引脚）
        │  python auto_pin_bind.py
        ▼
② auto_bind.cpp         （自动生成：nvboard_bind_all_pins 函数）
        │
        ▼
③ main.cpp              （调 NVBoard 的 API）
```

约束文件格式：第一行 `top=模块名`，之后每行 `信号名 引脚名`，向量信号写成 `信号名 (引脚MSB, ..., 引脚LSB)`。

`auto_pin_bind.py` 把它转成 C++ 绑定函数：

```cpp
void nvboard_bind_all_pins(Vtop* top) {
    nvboard_bind_pin( &top->sw,   2, SW1, SW0);
    nvboard_bind_pin( &top->ledr, 1, LD0);
}
```

NVBoard 的四个 API：

```c
nvboard_bind_all_pins(dut);   // 绑定引脚
nvboard_init();               // 初始化（开窗口）
nvboard_update();             // 每个周期更新：读开关、刷 LED
nvboard_quit();               // 退出
```

### 3. 引脚表（N4 板卡）

从 `nvboard/board/N4` 查得。`input` 表示板子→电路，`output` 表示电路→板子：

| 组件 | 引脚名 | 方向 | 数量 |
|---|---|---|---|
| 拨码开关 | `SW0`~`SW15` | input | 16 |
| 按键 | `BTNC` `BTNU` `BTND` `BTNL` `BTNR` | input | 5 |
| LED | `LD0`~`LD15` | output | 16 |
| 数码管 | `SEG0A`~`SEG7P` | output | 8 管 × 8 段 |
| VGA | `VGA_VSYNC` `VGA_HSYNC` `VGA_BLANK_N`、`VGA_R0-7`、`VGA_G0-7`、`VGA_B0-7` | output | — |
| PS/2 | `PS2_CLK` `PS2_DAT` | input | 2 |
| UART | `UART_TX`(output) `UART_RX`(input) | — | 2 |

**没有 `clk`、没有 `rst` 引脚**：时钟由 `main.cpp` 的 `single_cycle()` 翻转产生，复位由 `reset(n)` 函数做。所以不接板子的端口（clk、rst）不写进 `.nxdc`。

### 4. 双控开关上板

顶层改成带 `clk` 的版本（NVBoard 的循环需要时钟）：

```verilog
module top(
    input       clk,
    input [1:0] sw,
    output      ledr
);
    assign ledr = sw[0] ^ sw[1];
endmodule
```

约束文件 `constr/top.nxdc`：

```text
top=top

sw (SW1, SW0)
ledr LD0
```

拨动 `SW0`、`SW1`，`LD0` 按异或规律亮灭。**这一步走通了完整的“电路 → 约束 → 绑定 → 交互”链路。**

（补记：当时以为的 `make run` 其实并没有真的运行程序——详见第七节的说明。现象是直接运行构建出来的 `build/top` 确认的；`make run` 的配方现在已经补上，可以正常用。）

## 五、时序逻辑：流水灯

流水灯是一组 LED 依次点亮并循环，是第一个时序逻辑电路。讲义给的参考实现用 `always`：

```verilog
always @(posedge clk) begin
  if (rst) begin led <= 1; count <= 0; end
  else begin
    if (count == 0) led <= {led[14:0], led[15]};
    count <= (count >= 5000000 ? 32'b0 : count + 1);
  end
end
```

行为是：`count` 每个时钟 +1，涨到 5000000 归零；每次 `count` 归零时，`led` 循环左移一位。`count` 用来降低移动速度，否则人眼看不见。

我**先用 `always` 实现并让 NVBoard 跑通**（现象正确），但这不是 ysyx 要的写法。**随后用 `Reg` 把 `vsrc/light.v` 从 `always` 改写成了结构化建模**（两个 `Reg` 实例 + `assign`，无用户代码的 `always`），并与 `always` 版做了逐拍等价验证（`CNT_MAX=4`，1000 万拍零差异）。下面是当时用的改写思路和验收标准。

### 改写思路

1. 先把 `always` 块里的东西分成两类：**状态**（`cnt`、`led`，需要被“记住”的值）和**“下一状态怎么算”**（纯组合逻辑）。
2. 每个状态用一个 `Reg` 实例：`din` 接“下一状态”，`dout` 接“当前状态”。`Reg` 的参数和端口是 `#(位宽, 复位值)` 与 `(clk, rst, din, dout, wen)`——原来 `if (rst)` 那个分支，就是靠 `复位值` 参数实现的。
3. “下一状态”用 `assign` 写成表达式。原来的 `if (cnt == 0) led <= 移位;` 要翻译成“当 `cnt == 0` 时取移位后的值，否则取 `led` 自己”——一个二选一。**这一步是整道题的关键**：想清楚“条件不成立的那一拍，`led` 应该等于什么”。
4. 想清楚 `wen` 该接什么：`always` 里“某些拍不更新”对应到硬件是什么？（提示：如果一个状态的下一状态在“不更新”时等于它自己，写使能就可以恒有效。）
5. 自检：改完之后 `vsrc/light.v` 里不应该再出现 `always`（`vsrc/template.v` 里的官方模板不算）。对照《E4 学习计划》第 5 节那五条规范和三个自检问题。

### 验收标准

- `make lint` 干净，`make run` 现象与现在一致；
- “现象一样”不等于“逐拍一样”。更可靠的做法是**改造前后逐拍对照**：把 `Reg` 版和 `always` 版放在同一个测试平台里同时例化，写一个 C++ 驱动（像 `csrc/main.cpp` 那样手动翻 `clk`、调 `eval()`），每个上升沿之后比较两者的 `led`，跑上千万拍零差异；
- 让这个对照跑得快的小技巧：把 `5000000` 提成参数（例如 `CNT_MAX`），默认值不变，验证时用 `CNT_MAX=4` 就能把换灯周期压到 5 拍，几纳秒跑完 16 次循环。这个技巧后面做 ALU、状态机、sCPU 都会用到。

## 六、触发器与选择器模板

结构化建模的基础是两个官方模板，放在 `vsrc/template.v` 中。

### 1. Reg 模板

带复位和写使能的寄存器：

```verilog
module Reg #(WIDTH = 1, RESET_VAL = 0) (
    input             clk,
    input             rst,
    input  [WIDTH-1:0] din,
    output reg [WIDTH-1:0] dout,
    input             wen
);
    always @(posedge clk) begin
        if (rst)      dout <= RESET_VAL;
        else if (wen) dout <= din;
    end
endmodule
```

实例化格式 `Reg #(位宽, 复位值) 实例名 (clk, rst, din, dout, wen);`。它内部含 `always`，但这是官方模板，使用者只负责实例化。

### 2. MuxKey 模板

键值选择器。`MuxKey` 无默认值（键找不到输出0），`MuxKeyWithDefault` 带默认值：

```verilog
MuxKey #(NR_KEY, KEY_LEN, DATA_LEN) 实例名 (out, key, lut);
MuxKeyWithDefault #(NR_KEY, KEY_LEN, DATA_LEN) 实例名 (out, key, default_out, lut);
```

`lut` 是查找表，把每对写成 `{键, 数据}` 再拼起来。例：

```verilog
MuxKey #(2, 1, 1) i0 (y, s, {
    1'b0, a,
    1'b1, b
});
```

当 `s=0` 输出 `a`，`s=1` 输出 `b`。状态转移可以用它写：

```verilog
MuxKeyWithDefault #(4, 2, 2) mux (
    next_state, current_state, 2'b00, {
        2'b00, 2'b01,
        2'b01, 2'b10,
        2'b10, 2'b00,
        2'b11, 2'b00
    }
);
```

### 3. 内部实现的理解

- **`Reg`**：`always @(posedge clk)` 描述的是触发器的时钟端——不是“一段程序”，而是“每来一个上升沿把 din 锁存到 dout”。`<=` 是非阻塞赋值，保证多个寄存器同一时钟沿同时更新。
- **`MuxKey`**：外层 `MuxKey` / `MuxKeyWithDefault` 都只是实例化 `MuxKeyInternal`，差别在参数 `HAS_DEFAULT`。`MuxKeyInternal` 用 `generate for`（编译期展开，把扁平的 `lut` 切成一对对）拆出 `key_list` 和 `data_list`，再用 `always @(*)`（组合逻辑）逐项比较：键匹配的那一项通过门控，其余为0，最后 OR 起来就是被选中的数据。因为键互不相同，最多一项命中。

## 七、工具链上发现并修掉的两个问题

1. **`make run` 原来是个空规则。** `npc/Makefile` 末尾写了 `.PHONY: default all clean run`，却从来没有 `run:` 的配方，`make run` 只会打印一行 `make: Nothing to be done for 'run'.`——**它什么都没跑，而且不报错**。也就是说以前记的“`make run` 后现象正确”里，`make run` 那一步其实没有生效（现象是直接运行构建产物 `build/top` 看到的）。已补上配方：

   ```makefile
   run: $(BIN)
   	@$^
   ```

   现在 `make run` 会先构建再启动 NVBoard；实测 `timeout 5 make run` 连续运行 5 秒无异常（退出码 124，表示是被 timeout 正常掐掉的，不是崩溃）。

2. **`lint` 规则改用 `--top-module`。** 原来为了压掉 `MULTITOP`（多个候选顶层，因为 `template.v` 里的模块没有被例化）加了 `-Wno-MULTITOP`；直接指定顶层更准确，也不再有“多个候选顶层”这回事：

   ```makefile
   lint:
   	verilator --lint-only -Wall -Wno-DECLFILENAME --top-module $(TOPNAME) $(VSRCS)
   ```

   `make lint` 通过，输出只有 Verilation Report，没有任何 warning。

## 八、南大实验二：译码器和编码器（阶段 D）

这是阶段 D 的第一个南大数字电路实验。验收任务是“实现一个 8-3 优先编码器并在数码管上显示”。我把它拆成五个器件逐个做，每个先仿真测试、再合起来上板。

### 1. 五个器件与实现方式

| 器件 | 映射类型 | 实现方式 |
|---|---|---|
| 2-4 译码器 `decode24` | 规律 | 先用 `MuxKey`，后可简化为 `<<` |
| 3-8 译码器 `decode38` | 规律 | `assign y = en ? (8'b1 << x) : 8'b0;` |
| 4-2 编码器 `encode42` | 不规律 | `MuxKeyWithDefault`（键=4位独热输入，数据=2位编号，默认 0） |
| 七段译码 `bcd` | 不规律 | `MuxKey`（键=BCD，数据=8位段码） |
| 8-3 优先编码器 `encode83` | 优先链 | `assign` 嵌套三元（从 `x[7]` 往下），`valid` 为 `x` 的归约或 |

关键判断：**“能不能用公式算出来”决定用 `assign` 还是 `MuxKey`**。译码器能算，编码器和数码管不能。

### 2. `MuxKey` 的几个要点

- `NR_KEY` 是**实际写了几对**，不是键空间大小（`2^KEY_LEN`）；两者不等时用 `MuxKeyWithDefault`。
- `lut` 是**一根很宽的单信号**，用位拼接 `{键, 数据, 键, 数据, ...}` 拼成，不是“列表”。
- `{键, 数据}` 顺序写反了不会报错，只会选错值。

### 3. 测试

每个器件都写了 C++ 驱动，**穷举所有输入**，期望值独立计算（不照抄 RTL 的表）。测试抓到过真实 bug：

- `encode42` 的循环上界写成 `x<8`（应为 `x<16`），漏测了 `x=8`（应输出 3）那一组。**“测试通过”不等于“覆盖完整”。**
- 2-4 译码器的 `lut` 里键 `100` 的数据误写成 `0000`（应为 `0001`）。

### 4. 上板与极性

NVBoard 的数码管是**共阳（低电平点亮）**。官方示例 `seg.v` 内部存“高电平点亮”的表，输出前用 `~` 取反。我的 `bcd.v` 一开始直接输出高电平表，上板会显示反的——**加 `~` 才对**。这类“极性”问题**仿真测不出来**（仿真只比你写的表），只有上板才暴露。

### 5. 验收现象

拨 `SW7~SW0`，结果：

| 输入 | LED2-0 | 指示位 LD4 | 数码管 |
|---|---|---|---|
| `00001110` | 011 | 1 | 3 |
| `10000000` | 111 | 1 | 7 |
| `00000001` | 000 | 1 | 0 |
| `00000000` | 000 | 0 | 0 |

第 3、4 组最能验证“编码位”和“指示位”是两条独立的线。

## 九、南大实验三：加法器与 ALU（阶段 D）

验收任务是“实现一个带有逻辑运算的 4 位补码 ALU”。按六个子步骤推进，每步都用 C++ 驱动穷举验证。

### 1. 一位全加器

门级实现：

```verilog
assign s    = a ^ b ^ cin;
assign cout = (a & b) | (a & cin) | (b & cin);
```

期望值直接用 `{cout, s} = a + b + cin` 独立算出，穷举 8 种全过。

### 2. 4 位行波进位加法器

用 `generate for` 把 4 个全加器级联，进位链是一根 `carry[4:0]`（`carry[0]=cin`，每个全加器的 `cout` 接 `carry[i+1]`，`carry[4]` 是总进位）。穷举 512 种全过。比手写 4 个实例更通用——位数改了只改循环上界。

### 3. 4 位补码加减法器

减法转加法：`A - B = A + (~B) + 1`。一个 `Sub` 控制端同时管两件事：把 B 按位取反、给加法器的进位输入置 1。

```verilog
wire [3:0] Bx = B ^ {4{Sub}};
add4 u_add (.a(A), .b(Bx), .cin(Sub), .s(Result), .cout(Carry));
assign Overflow = (A[3] == Bx[3]) && (Result[3] != A[3]);
assign Zero     = ~(|Result);
```

**踩到的坑**：溢出公式一开始比的是 `B[3]` 而不是 `Bx[3]`。做减法时加法器真正相加的第二个操作数是 `Bx`（即 `~B`），不是 `B`——比错了会在一半的减法用例上误判溢出（512 个里错 128 个）。改成 `Bx[3]` 后全过。

这正是讲义思考题 1 的点：减法把 `+1` 折进去之后，“两个加数”是 `A` 和 `~B`，不是 `A` 和 `B`。

### 4. 4 位 ALU

八种功能并行算出来，用 `MuxKey` 按 3 位功能码选一个：

- 加减：复用加减法器（`Sub` 要覆盖“减法”和“比较”三种功能）
- 逻辑：`~A`、`A&B`、`A|B`、`A^B`
- 比较：`Less_s = Result[3] ^ Overflow`（带符号小于），`Eq = ~(|Result)`

穷举 `16 × 16 × 8 = 2048` 种。

**踩到的坑（两个都出在测试代码里）**：

1. `exp_res =- a & b;` —— `=-` 被解析成 `= (-a) & b`（负号），算的不是 `a & b`。少了一个空格。
2. `unsigned t_b = (f == 1) ? ((~b) & 0xF) : (unsigned)t_b;` —— 初始化式里引用了自己，`else` 分支拿到未初始化的值。应该写 `(unsigned)b`。

两个都是“编译器不报错、只有测试能抓到”的错。

### 5. 上板验收

`SW7-4` → A，`SW3-0` → B，`BTNL/BTNC/BTNR` → sel，`LD3-0` → res，`LD4/5/6` → carry/of/zero。八种功能逐一核对，全部正确。

（把 sel 从 `{BTNC,BTNU,BTND}` 改成 `{BTNL,BTNC,BTNR}`——L/C/R 三个横排键更好按，不易误触。）

### 6. 思考题

- **减法 Overflow 两种实现哪个对？** 方法一（`+1` 走加法器的 `Cin`）正确；方法二把 `+1` 先折进 `t` 再相加，结果被截断到 n 位，当 B 是最小负数时丢位、误判溢出。
- **Zero 用 `if` 比较还是用一元约减？** 用 `~(|Result)`——把各位或起来再看是不是全 0，几个逻辑门即可；用比较器面积和延迟都更大。

## 十、南大实验六：移位寄存器、桶形移位器与 LFSR（阶段 D）

验收任务是"移位寄存器及桶形移位器"。我在此基础上又加做了一个 8 位 **LFSR 伪随机数发生器**并上板显示。

### 1. 移位寄存器

结构化写法：用 `Reg` 存当前值，用 `assign` 加位拼接 `{}` 描述"下一状态"。左移是 `{q[N-2:0], din}`（高位移出、低位补入），右移是 `{din, q[N-1:1]}`；"要不要更新"交给 `Reg` 的 `wen`，"装载还是移位"交给选择器（`MuxKeyWithDefault`）挑下一拍的 `din`。

我真正卡过的是**位拼接 `{}` 的方向**：左端是高、右端是低，动手前先想清"哪一位被移出、哪一位补进来"，否则会移反。

### 2. 桶形移位器

桶形移位器的结构是**分级选择器**：把"移 n 位"拆成"移 1 位、移 2 位、移 4 位……"几级，每级一个选择器，按移位量对应位决定"过不过这一级"。N 位只要 log₂(N) 级，延迟与移位量无关。全程 `assign` + `MuxKey`，无 `always`。

### 3. LFSR 伪随机数发生器（另加）

8 位 LFSR，反馈抽头 `x8 = x4 ⊕ x3 ⊕ x2 ⊕ x0`，复位值 `01`，并把全 0 状态强制回 `01`（防锁死）：

```verilog
wire       fb  = q[4] ^ q[3] ^ q[2] ^ q[0];
wire [7:0] nxt = (q == 8'b0) ? 8'h01 : {fb, q[7:1]};
Reg #(8, 8'h01) u_q (.clk(clk), .rst(rst), .din(nxt), .dout(q), .wen(en));
```

**仿真测试的大坑**：一开始报 253 条 FAILED。逐拍对照后确认**硬件完全正确**（从 `01` 出发的序列 `01 80 40 20 10 88 c4 e2 …`，周期 255，与参考一致）——错在**测试里算期望值那一行**：`(cur >> 0)` 误写成 `(cur > 0)`，`>` 是比较、结果恒为 1，等价于对 `x4⊕x3⊕x2` 取同或，那条错误链周期只有 62，于是和正确硬件对不上。

教训：`>` 与 `>>` 只差一个字符、编译器不报警（比较和移位都是合法运算），只能靠测试抓；另外 C 里 `&` 优先级高于 `^`，写 `a^b^c^d` 再 `&1` 时最外层要加括号。测试里补了"255 拍后 `q` 必须回到 `01`"这一条，专门挡"周期偏短"。

### 4. 上板

LFSR 每个时钟都前进，全速跑肉眼看不见，所以用**按钮手动步进**：

- `top.v`：用一个 `Reg` 把按钮同步一拍得 `btn_d`，`step = btn & ~btn_d` 只在按下那一拍为 1（**不把按钮直接当时钟**，那样会抖）。
- `lfsr` 加 `en` 端口接到 `Reg` 的 `wen`，按钮没按就不更新。
- 新增 `hex7seg`（4 位十六进制 → 7 段，`MuxKey` 查表，覆盖 0~F，和实验二的 `bcd` 同类），把 `q[7:4]`、`q[3:0]` 各接一个数码管；**共阳要取反**：`assign seg = ~code;`。
- `constr/top.nxdc` 里小数点引脚是 `DEC0P`/`DEC1P`（**不是** `SEG0P`；这个名字我猜错过一次，`auto_pin_bind.py` 直接报 `Invalid pin SEG0P`）。

现象：开窗显示 `01`，每按一下 `BTNC` 按 LFSR 序列变一次（`01→80→40→20→10→88…`）。

> 注：`shift_reg.v`、`barrel_shift.v` 的源码目前在 WSL `~/e4/NJU_exp/exp6/`，尚未同步到 E 盘快照；第 1、2 小节按设计整理，细节以 WSL 源码为准。

## 十一、南大实验七：状态机及 PS/2 键盘输入

本次练习的实际代码位于 WSL 的 `/home/ysyx/e4/NJU_exp/exp7`。Windows 仓库中的本文件保存学习记录，不代表 WSL 源码已经同步到仓库。参考资料为[南大实验七讲义](https://nju-projectn.github.io/dlco-lecture-note/exp/07.html)。

### 1. 从状态机到键盘输入

实验先进行了连续四个相同输入的状态机练习，随后将顶层改为 PS/2 接收器，再接入按键处理、ASCII 查表与数码管显示。当前 `fsm.v` 保留在目录中，但键盘版顶层不再例化它。

我区分了三种职责：接收器负责把串行信号拼成扫描码字节，按键处理模块负责解释按下、重复和松开，显示模块负责把键码与 ASCII 转成数码管段码。

| 文件 | 作用 |
|---|---|
| `ps2_keyboard.v` | 同步键盘时钟、检测下降沿、接收与检查帧、将字节存入 FIFO |
| `key_handler.v` | 自动取走 FIFO 字节，识别按下与松开，保存字符键和修饰键状态，累计字符按键次数 |
| `scancode_to_ascii.v` | 将 26 个字母和主键盘 10 个数字的扫描码映射为基础 ASCII，并输出有效标志 |
| `hex_to_seg.v` | 将一个 4 位十六进制数转换成七段段码，支持显示使能 |
| `top.v` | 连接各模块，处理 Shift 的大小写与数字符号转换，拆分六位显示数据 |
| `main.cpp` | 产生 PS/2 输入时序，自动检查状态、计数、ASCII 和代表性的段码输出 |
| `board_main.cpp` | NVBoard 引脚绑定、复位、板卡更新和系统时钟驱动 |
| `constr/top.nxdc` | 将顶层端口绑定到键盘、LED 和数码管引脚 |

### 2. PS/2 收帧与 FIFO

一帧有 11 位：起始位 0、低位先发送的 8 位数据、奇校验位、停止位 1。接收器在检测到 `ps2_clk` 下降沿后采样。`buffer` 保存前 10 位，第 11 位直接从 `ps2_data` 检查，因此接收缓冲只需要 10 位。

只有起始位、停止位和奇校验都正确，数据字节才写入 FIFO。`ready=1` 表示队首字节有效，`next_data_n=0` 表示消费者确认取走当前字节。

FIFO 对应生产者—消费者模型：接收逻辑生产字节，`key_handler` 消费字节。读取确认是数据交接，不是互斥锁；生产者和消费者可以在同一拍分别写入、读取。

初期接收器测试包括单字节 `1C`、三字节不读后按序取出，以及连续八字节写入和读回。按当前沿用讲义的告警逻辑，前七字节不设置 `overflow`，第八字节设置，但八个字节仍能按序读出；继续写入会覆盖未读数据。`overflow` 保持到复位，不会因队列读空而清除。这不是具有满队列写入阻止功能的完整 FIFO。

### 3. 普通按键状态与计数

`key_handler` 用 `Reg` 保存状态，用组合表达式计算下一状态。`consume=ready & clrn`，`next_data_n=~consume`：在每个允许消费的上升沿，按键处理模块使用旧队首数据更新状态，接收器同时前移读指针。

| 状态变量 | 含义 |
|---|---|
| `break_pending` | 已收到 `F0`，等待后面的松开键码 |
| `pressed` | 当前有一个受支持的字符键按住 |
| `keycode` | 最近一次新按下的字符键扫描码 |
| `press_cnt` | 字符键的新按下次数，长按重复不增加 |

以 A 为例：第一次收到 `1C` 保存键码、设置 `pressed` 并增加次数；继续收到 `1C` 只保持状态；收到 `F0` 设置等待记号；后续收到匹配的 `1C` 才清除 `pressed`。松开后保留键码和次数，由显示使能关闭低四位。

调试时曾将 `prefix_event` 对应的 `next_break_pending` 误写为 0，导致无法记住 `F0`，`pressed` 一直为 1，次数停在 1。64 项测试中出现 55 项连锁失败；改为 1 后通过。这个问题说明应从第一处状态错误追踪后续失败，而不是把每条失败都当成独立问题。

### 4. ASCII 与七段显示

基础转换表用 `MuxKeyWithDefault` 实现，共 36 对键值。每个表项输出 `{有效标志, ASCII}`，表外输入输出全零。默认值为零时，当前模板的 `MuxKey` 也能实现同样功能；它不要求填满所有可能的键值，参数数量表示实际表项数量。

`hex_to_seg` 支持 `0～F`，内部使用高电平点亮的表，输出统一取反；禁用时输出 `8'hFF`，对应低有效数码管全灭。

| 数码管 | 显示内容 | 使能 |
|---|---|---|
| 第 1、0 位 | 扫描码高、低四位 | `pressed & ascii_valid` |
| 第 3、2 位 | ASCII 高、低四位 | `pressed & ascii_valid` |
| 第 5、4 位 | 字符按键次数高、低四位 | 始终显示 |
| 第 7、6 位 | 不使用，输出固定为 `8'hFF` | 始终熄灭，界面控件保留 |

扫描码与 ASCII 两组的显示使能均为 `pressed & ascii_valid`。次数按十六进制显示，`09` 后是 `0A`，第 16 次显示 `10`；8 位次数达到 255 后再增加会回到 0。

按下 A 的目标显示为 `01 61 1C`，松开后仅保留次数 `01`。新增五项代表性显示检查后，基础版共 69 项检查通过。

### 5. Shift、Ctrl 选做功能

字符键和修饰键分开保存。Shift、Ctrl 不占用 `pressed`，也不增加字符按键次数，因此可以与一个字母或数字同时按住。

| 状态／寄存器 | 接线与作用 |
|---|---|
| `extended_pending`／`u_extended` | 记住 `E0` 前缀，区分扩展键；经过 `F0` 时仍保留，处理实际键码后清除 |
| `modifiers[0]`／对应 `u_modifier` | 左 Shift，通码 `12`，断码 `F0 12` |
| `modifiers[1]`／对应 `u_modifier` | 右 Shift，通码 `59`，断码 `F0 59` |
| `modifiers[2]`／对应 `u_modifier` | 左 Ctrl，通码 `14`，断码 `F0 14` |
| `modifiers[3]`／对应 `u_modifier` | 右 Ctrl，通码 `E0 14`，断码 `E0 F0 14` |
| `shift_down`、`ctrl_down` | 分别对左右状态取或，松开其中一个不会误清除另一个 |
| `u_filter` | 对当前收到的 `data` 查表，只有非扩展且受支持的字母／数字才能成为新的字符按键 |

顶层根据当前 Shift 状态实时转换 ASCII：小写字母减去 `20h` 得到大写，数字用查表转换为美式键盘符号。例如 Shift+A 输出 `41`，Shift+1 输出 `21`（`!`）。字符仍按住时松开 Shift，ASCII 会变回基础编码，次数不增加。

Ctrl 当前实现按住状态指示，不将 Ctrl+A 转换成控制字符 `01`。Caps Lock、多普通字符键同时按住和完整扩展键支持不在当前实现范围内。

### 8. 学习收获

我逐渐理解了前缀状态的作用：`F0` 和 `E0` 本身不代表一个完整按键事件，必须保存它们，才能解释后面的键码。寄存器保存的是历史信息，组合逻辑根据当前输入与历史信息决定下一状态。

`pressed` 类似对新按下事件设置一道门，防止长按重复计数；它不会阻止扫描码继续接收和消费。这与 FIFO 的生产者—消费者交接是两层不同的机制。

## 十二、南大实验八：VGA 接口控制器（阶段 D）

### 1. 目标与结构

在 640×480@60Hz 的时序下，把一张图片（`imgs/ysyx.png`）显示到 VGA 上，并配一个 C++ 驱动做逐拍验证。拆成两个模块：

- `vga_ctrl`：只产生扫描时序与坐标——`x_cnt`(1..800)、`y_cnt`(1..525) 两个计数器，`hsync`/`vsync` 同步信号，`valid` 有效区标志，`h_addr`/`v_addr` 有效区地址。
- `top`：拼 19 位显存地址 `{h_addr, v_addr[8:0]}`、例化 `Rom` 取色、把 `hsync`/`vsync`/`valid` 各延一拍与颜色对齐、输出 RGB444→RGB888。

显存用 `common/template.v` 里的 `Rom` 模板（同步读），初始化文件 `imgs/mem.hex` 由 `img2hex.py` 从 PNG 生成。**Rom 放在 `top`、不放 `vga_ctrl`**：一来保住已测好的 `vga_ctrl`，二来测计数器时不必连带加载整块显存。

### 2. 关键参数

| 项 | 值 |
|---|---|
| 行计数 | `x_cnt` 1..800（同步 1–96、后肩 97–144、显示 145–784、前肩 785–800） |
| 列计数 | `y_cnt` 1..525（同步 1–2、后肩 3–35、显示 36–515、前肩 516–525） |
| 有效区 | `x∈[145,784] && y∈[36,515]`，正好 640×480 |
| 地址 | `addr = {h_addr, v_addr[8:0]}`（列优先，h 高 10 位、v 低 9 位） |
| 显存 | 640×512 = 327680 字，每字 12 位 RGB444 |

### 3. 验证链（Verilator 逐拍穷举，`PASS: 420000` = 一整帧 800×525）

| 子块 | 期望来源 | 关键点 |
|---|---|---|
| 计数器 `x_cnt`/`y_cnt` | 规格递推（来源 A） | 复位值 = 1（不是 0） |
| `hsync`/`vsync`/`blank` | 文档时序区间（来源 C） | 低有效 |
| `h_addr`/`v_addr` | 规格减法（来源 A） | 用**分开的** `h_valid`/`v_valid`，不能用组合 `valid` |
| `color` | 显存文件（来源 A） | **整体错一拍**：延迟信号对上一拍坐标 |

每块都做了**变异测试**（改坏 RTL，测试必须 FAILED）：回绕点 `800→799`、`hsync` 极性、有效区边界、地址拼接反序、去掉 1 拍延迟——全部被抓住。最后 NVBoard 上板，图象不偏、不花、颜色正确。

### 4. 本次报错与踩坑清单

#### 4.1 Verilog / lint

| # | 报错 | 原因 | 修法 |
|---|---|---|---|
| 1 | `UNUSEDSIGNAL: 'h_addr'/'v_addr'` | 声明并连到实例，但没人读（颜色通路还没接） | 用得上才声明；或引成 output 端口 |
| 2 | `PINMISSING: Instance has missing pin 'h_addr'` | 把连接删掉后，Verilator 又要求实例引脚齐全 | 把 `h_addr`/`v_addr` 引成 top 的 output 端口——既接上、又是端口，两种警告都免 |
| 3 | `Duplicate declaration of signal: 'addr'` | `addr`/`color` 已进端口表，又写了一遍 `wire` | 端口即 wire，删掉重复声明；`addr` 改用 `assign` 驱动 |
| 4 | `UNUSEDPARAM: 'DEPTH'` | `Rom` 里存储器写死 `[0:327679]`，参数没用到 | 改成 `[0:DEPTH-1]` |

### 5. 设计上的三个易错点（非报错，但值得记）

- **复位值与对齐陷阱**：计数器复位值是 1；`reset()` 尾部若多走一拍，`x_cnt` 会变成 2，模型若不对齐就整体错一拍。
- **有效区地址要分开算**：`h_addr` 只由 `h_valid`（x）决定、`v_addr` 只由 `v_valid`（y）决定，不能用组合的 `valid`——否则"x 在显示区、y 在消隐区"的那些行会算错。
- **1 拍延迟对齐**：`Rom` 同步读让颜色晚一拍，必须把 `hsync`/`vsync`/`blank` 各延一拍去跟颜色对齐，否则图像右移一像素。这个错肉眼看不出，只有逐拍测试能抓。

### 6. 选做：弹性碰撞

在实验八基础上又做了一步选做——让一张 100×100 的小图在屏幕内按固定方向、不同速度移动，碰到屏幕边界按弹性碰撞方式反弹，类似弹球游戏。

**结构**：另起 `exp8/ball/` 子目录，与主实验隔离。里面 `ball.v`（位置 + 方向 + 反弹）、`top.v`（`vga_ctrl` + `ball` + 颜色 mux）、`vga_ctrl.v`（从父目录复用）、`main.cpp`，以及一整套 `Makefile`/`Makefile.board`/`constr/top.nxdc`。

**`ball.v` 的要点**：

- 用左上角坐标 `ball_x`/`ball_y` 表示位置，范围 `x∈[0,540]`、`y∈[0,380]`（屏幕 640×480，图 100×100）。
- 速度取常量 `vx=4`、`vy=3`（两轴不同）；方向各用 1 位 `dir_x`/`dir_y` 表示（0=右/下、1=左/上）。
- **反弹用"预判下一步"**：先算按当前方向走一步会到哪，只有"下一步会越界"时才贴边并翻转方向——这样撞边后下一帧就离开，不会卡在墙上。

**`top.v` 的要点**：

- 帧节拍 `frame_tick = (x_cnt==1 && y_cnt==1)`，接到 `ball` 的 `en`，让图**每帧移动一次**而不是每个像素时钟。
- `in_ball` 用"半开区间"（`h_addr∈[ball_x, ball_x+100)`）判断像素在不在图内，球内出红色、球外出黑色。
- 这里**没有 Rom，所以不需要 1 拍延迟**——延迟本是同步存储器带来的，不是 VGA 固有的。

**验证**：`ball` 单独作 DUT（`Makefile` 的 `TOPNAME=ball`），每拍当一帧来驱动，跑 20000 帧覆盖多次全往返，`PASS: 80000`。除了逐帧比对位置和方向，还在**每一帧开头**做一次 `en=0` 探针，确认门控有效。

**变异测试**（这次的重点）。刻意改坏 `ball.v`，看测试是否报警：

| 改动 | 预期 | 说明 |
|---|---|---|
| `right_wall` 540 → 539 | FAILED | 边界位置错，反弹点偏移 |
| `vx` 4 → 5 | FAILED | 每帧步长错 |
| 去掉 `next_dir_x` 里的取反 | FAILED | 撞墙不翻向 |
| `hit_left` 的 `<` 改成 `<=` | FAILED | 贴边后仍满足撞墙条件，卡死 |
| `u_dir_x` 的 `.wen(en)` → `.wen(1'b1)` | 需配合探针位置 | 见下 |

前四个都被直接抓住。**第五个一开始没抓到**，反而暴露了测试的盲区：`en=0` 探针原本放在复位后、探的是初始位置 `(270,190)`——而 `dir_x` 的下一拍值在那**恰好等于当前值**（远离墙，`next_dir_x = dir_x`），所以就算 `wen` 失效、每拍都更新，也看不出变化。

修正：把 `en=0` 探针**挪进主循环、每帧开头探一次**。这样 20000 帧会扫过几千个状态，其中包含 `(538,0)` 这种"撞右墙前一帧"——在那里 `next_dir_x = ~dir_x`，`dir_x` 若不门控会当场翻转，探针立刻抓到。

这让我记住一条：**门控测试的探针必须落在"寄存器本来就会变化"的状态上**。若探针所在状态里该寄存器本就不变，就算 `wen` 坏掉也测不出来。这条盲区不是靠"多跑几帧"发现的，而是靠**变异测试**——这正是变异测试的价值：它不仅确认测试能抓错，还会反过来指给你"哪里其实没测到"。

### 7. 学习收获

这一章最实在的收获，是亲手走完了一套**验证方法**：拿到模块先答"四问"（输入有几个及范围 / 期望怎么算 / 组合还是时序 / 比对哪些输出），期望值从三个来源（直接运算、朴素算法、区间定义）独立算出，组合逻辑穷举、时序逻辑逐拍，最后用**变异测试**证明测试真能抓错。四块 RTL 的 C++ 驱动都是照这个流程写下来的。

另一个体会是"**能跑通"和"改对了"是两件事**：`PASS` 只说明"模型和当前 RTL 一致"，要故意改坏 RTL 看测试是否报警，才算数。这次遇到的不少 bug（漏 `else`、少 `%`、忘调用 `load_mem`、多余的循环）都是"编译能过、逻辑错了"的类型——正是测试把它们揪出来。

还有一点：**看得见的错靠眼睛，看不见的错靠测试**。图像右移一像素这种事，上板肉眼几乎看不出来，但逐拍比对能精确定位到每一拍。

## 十三、用 RTL 实现 sCPU（阶段 E）

### 1. 目标与结构

把 F 阶段用 Logisim 设计的 sCPU，用 RTL 重新描述一遍，运行 `1+2+...+10`，并通过 `io` 指令把结果输出到 NVBoard 的 LED。代码在 `~/ysyx-workbench/npc/`：

- `vsrc/scpu.v`：数据通路 + 控制（PC、译码、GPR 接口、ALU、分支、io）
- `vsrc/gpr.v`：4×8 位寄存器组（`generate` + 每寄存器一条 `Reg`）
- `vsrc/inst_rom.v`：用 `MuxKeyWithDefault` 实现的指令 ROM
- `vsrc/top.v`：上板顶层（例化 `scpu`，引出 `led`）
- `test/main.cpp`：C++ 测试（单独编译，`--top-module scpu`）

### 2. 关键设计

实现的是**增强版 sISA（F6）**：

| 指令 | 编码 `[7:6] | [5:4] | ...` | 行为 |
|---|---|---|---|
| add | `00 | rd | rs1 | rs2` | `R[rd] = R[rs1] + R[rs2]` |
| li（增强） | `10 | rd | s | imm` | `R[rd] = imm << (2*s)` |
| bner0（增强） | `11 | offset | rs2` | `if (R[0] != R[rs2]) PC = PC + sign_ext(offset)` |
| io | `01 | rd | i/o | idx` | `i/o=1`：`dev[idx] = R[rd]` |

- **译码**：抽字段 + 独热控制信号（`is_li`/`is_add`/`is_bner`/`is_io`）。
- **写回**：`wdata` 在选择器里选（li 立即数 / 加法结果）；`w_reg = is_li | is_add`（io、bner0 不写 GPR）。
- **GPR 读口复用**：`raddr1`/`raddr2` 按指令选（add→rs1/rs2、bner0→0/rs2、io→rd）。
- **LED 锁存**：io 输出必须经过一个**独立的输出寄存器**（`Reg`），只在 io 执行时写入——否则 GPR 一变、LED 就跟着变。
- 程序（`inst_rom`）计算 `1+...+10`，最后 `io` 把 `R2=55` 打到 LED。

### 3. 验证

- **功能**：C++ 测试跑完程序，检查 `pc=10, R0=10, R1=10, R2=55, R3=1, led=55` → `PASS: 6 checks`。期望值由**手推程序语义**独立得到（不抄 RTL）；读 DUT 内部 GPR 用 `dut.rootp->scpu__DOT__u_gpr__DOT__regs[i]`。
- **变异测试**：7 个变异里 6 个被抓（`add` 改减、`!=` 改 `==`、符号扩展改零扩展、`pc+2`、`w_reg` 去掉 `is_add`、`wdata` 恒选 `li_data`）；剩下 1 个是**覆盖洞**——`w_led` 去掉 `& io_dir` 仍 PASS，因为程序只用到了"输出到 LED"这一种 io，没覆盖 io 的方向位/设备号。这是**测试的边界**，不是测试写错。

### 4. 上板

`top.v` 例化 `scpu` 引出 `led`；`constr/top.nxdc` 映射 `led (LD7,...,LD0)`；`make run`。NVBoard 上 LED 显示 `0b0011_0111 = 55`（LD5/LD4/LD2/LD1/LD0 亮）。

### 5. 实现中的坑

- `io_idex` 拼写错（应为 `io_idx`）。
- `is_io` 在声明之前被 `raddr2` 用到（Verilog 要求先声明后使用）。
- `offset_ex` 多写了 `2'b11`（4+4+2=10 位 → 截断成 8 位，偏移算错）——变异测试当场抓到。
- 测试读内部信号前要 `#include "Vscpu___024root.h"`，否则 `Vscpu___024root` 只是前向声明、是不完整类型。
- 手动编测试时源码路径要用 `$(pwd)` 绝对路径（`--build` 生成的 makefile 在 obj 目录里跑，相对路径找不到）。
- 测试文件别放 `csrc/`：`Makefile` 的 `find ./csrc` 会把它的 `main()` 也收进来（双 `main`）。

### 6. 学习收获

这一章把前面学的东西**串起来用了一遍**：结构化建模（`Reg`/`MuxKey`/`assign`）、译码器当查找表、选择器做控制、以及"期望值独立手算 + 变异测试"这一整套验证方法。sCPU 里"多条指令抢同一个部件"（写口的数据来自 li 或 add、读口地址来自 rs1 或 0 或 rd）正是数据通路与控制逻辑的典型冲突，而**用一个选择器按指令类型统一解决**，是这一章最核心的设计思想。

另一个很实在的体会：**变异测试既证明测试能抓错、又指出测试的边界**。第 7 个变异"抓不到"这件事，本身就是一条比"6 个都抓到"更有价值的信息——它明确告诉我们测试覆盖到哪里为止。

## 十四、sEMU 与 DiffTest（阶段 F）

### 1. 从电路实现到指令集模拟器

完成 sCPU 后，我用 C++ 写了一个指令集模拟器 sEMU。两者实现同一套增强版 sISA：sCPU 用寄存器和组合逻辑描述电路，sEMU 用变量保存状态、用语句实现指令语义。当前 sCPU 是单周期处理器，一个时钟上升沿执行一条指令；sEMU 每调用一次 `step()` 执行一条指令。

模拟器的状态集中在 `CPUState` 中：8 位 `pc`、4 个 8 位寄存器 `r[4]` 和 8 位 `led`。程序 ROM 单独保存，当前指令、opcode 和操作数字段只作为 `step()` 中的临时变量。这样能把“需要记住的状态”和“根据指令临时算出的值”分开。

### 2. 文件结构与接口

代码沿用 WSL 的 `~/ysyx-workbench/npc/`，同步到仓库后位于 `e/e4/npc/`：

```text
npc/
├── vsrc/                  RTL：scpu、gpr、inst_rom、top、template
├── csrc/
│   ├── main.cpp           NVBoard 仿真入口
│   └── semu/
│       ├── semu.h         CPUState 和 SEMU 接口声明
│       └── semu.cpp       程序 ROM、复位和单条指令执行
├── test/
│   ├── main.cpp           sCPU 最终结果检查
│   ├── semu_main.cpp      sEMU 独立测试入口
│   ├── difftest.cpp       sCPU 与 sEMU 逐条比较
│   └── scpu_fetch.cpp     早期取指练习
├── constr/top.nxdc        NVBoard 引脚绑定
├── Makefile               NVBoard 构建与运行
└── Makefile.test          sEMU 和 DiffTest 构建与运行
```

sEMU 核心没有 `main()`，只提供 `reset()`、`step()` 和 `get_state()`。独立测试与 DiffTest 分别提供自己的入口，共用同一份模拟器实现，避免重复写指令语义。

### 3. 单条指令怎样执行

`step()` 按取指、译码、执行写回、更新 PC 的顺序实现：先用当前 PC 读取 ROM，拆出指令字段，再根据 opcode 更新状态。默认 `next_pc = pc + 1`，跳转成立时覆盖这个值，最后才写回 PC。

| 指令 | sEMU 中的状态转移 |
|---|---|
| `add` | 读取旧的两个源寄存器，相加后写入目的寄存器，保留低 8 位 |
| 增强版 `li` | `R[rd] = imm2 << (2 * sel)` |
| 增强版 `bner0` | 若 `R0 != R[rs2]`，下一 PC 为当前 PC 加 4 位有符号偏移量 |
| `io` | 当前只实现输出方向、设备号 0：把 `R[rd]` 写入 LED；其他 io 不改变 GPR 和 LED |

跳转最容易混淆的是基址和符号扩展。地址 8 的 `F9 = 11 1110 01` 表示比较 R0、R1，偏移量 `1110` 是 -2，所以条件成立时跳到 `8 - 2 = 6`，不是先加一再跳。C++ 中先取出偏移量 0～15，最高位为 1 时减去 16，就能得到 -8～7。

sEMU 单独执行 50 条指令后检查 `PC=10、R0=10、R1=10、R2=55、R3=1、LED=55`，实际输出 `PASS: 6`。

### 4. DiffTest 的比较时机

DiffTest 以 RTL 的 sCPU 为 DUT，以 sEMU 为 REF。两边先复位到相同状态，每次循环先保存执行前的 PC 和机器码，再调用 `tick(dut)` 与 `ref.step()`，最后比较两边执行后的 PC、四个 GPR 和 LED。50 条指令、每条 6 项检查，实际输出 `PASS: 300`。

这次直接用 `--top-module scpu`，因为 `scpu` 已经有 PC、指令输出，读取内部 GPR 也更方便；`top.v` 则用于连接 NVBoard。测试包含 `Vscpu___024root.h`，并使用 `--public-flat-rw` 保留内部寄存器，访问路径为 `dut.rootp->scpu__DOT__u_gpr__DOT__regs[j]`。

比较时机必须对齐：不能在 RTL 已经执行、sEMU 还没执行时比较。报错定位也要保存执行前的 PC 和指令，因为时钟更新后 `dut.pc`、`dut.inst` 已指向下一条指令。

### 5. 完善报错与检查 PC

测试沿用我之前的写法：`fails` 记录失败项，`total` 记录检查项，逐项打印实际值和期望值，同一条指令检查结束后如果有差异就立即停止。报错包括执行序号、出错指令的 PC 和机器码，以及不同 GPR 或 PC 的实际值和期望值。

PC 也纳入比较。`bner0` 不写 GPR，只比较寄存器可能无法在跳错的那一拍发现问题；比较执行后的 PC 就能立即定位。

### 6. 错误注入验证

我分别只改 RTL，保持 sEMU 正确，检查 DiffTest 能否抓到第一处差异：

| 临时改动 | 实际报错 | 定位 |
|---|---|---|
| `add_res` 额外加 `8'd1` | `r0=11 (expect r0=10)`，`step=3: pc=02 inst=01`，`1/18` 项失败 | 第三条指令把 8 和 2 相加，错误结果多 1 |
| `branch_target` 额外加 `8'd1` | `pc=7 (expect pc=6)`，`step=9: pc=08 inst=f9`，`1/54` 项失败 | 第一次执行循环跳转就发现目标地址错误 |

错误注入时测试返回 1，Makefile 因此报 `Error 1`，外层 make 返回非零，这是预期的失败。每次测试后恢复原表达式，重新编译；两处错误都恢复后再次运行，得到 `PASS: 6` 和 `PASS: 300`。

### 7. Makefile 与上板验收

### 8. 实现中的问题与当前边界

- `CPUState` 结构体结束需要 `;`，`static_cast` 曾误写成 `state_cast`。
- 编译找头文件用 `-I`（大写 I），不是 `-l`；运行路径必须对应 `-o` 指定的文件名。
- `totals`、`epx_led` 和 `printf` 中的 `r%`、`&d` 拼写错误导致编译报错或警告，修正后重新编译。
- 指令循环和寄存器循环要分别用 `i`、`j`，报错中的指令序号不能误用寄存器编号。
- 早期 `scpu_fetch.cpp` 假设 PC 每拍加一，这不适用于已经加入跳转的完整 CPU；当前验收以 `difftest.cpp` 为准。
- 目前只运行固定的求和程序，50 条指令后的状态一致不代表整个指令空间都经过验证。io 也只实现 LED 输出，没有覆盖拨码输入、其他设备或所有边界条件。

这部分最实在的收获是把验证从“最后等于 55”推进到“每条指令后的状态都一致”。错误注入进一步证明，寄存器计算错误和 PC 跳转错误都能在第一次出现差异时被定位，而不用等到程序最终结果出错再翻大量波形。

## 十六、学习收获与反思

从 C 转到 RTL 最大的障碍是**思维方式**：Verilog 不是“一段会执行的程序”，而是“一张电路的描述”。一开始我按学 C 的习惯，用 `always` 加 `if/else` 去“写逻辑”，能跑通，但这不是 ysyx 要的方式。

理解 `Reg` 和 `MuxKey` 之后，思路变了：电路 = 寄存器（存状态）+ 组合逻辑（算下一个状态）。参考实现里一个 `always @(posedge clk)` 的 `if/else`，可以拆成“`Reg` 实例存当前值”加“`assign` 算下一个值”两部分——这个拆分就是结构化建模的核心，也是最需要亲手练的一步。

NVBoard 的接入让我第一次“看见”电路工作：拨开关、看灯亮，比只看波形直观。约束文件、自动绑定、`main.cpp` 的 API 调用三者配合，是一套可复用的验证流程，后面所有实验都建立在这套流程上。

一个方法论上的提醒：**“能跑通”和“改对了”是两件事**。改写之后现象一样可能只是碰巧，所以要有意识地做“改造前后逐拍对照”，而不是只看板子上灯在动。

另外，`make run` 那个空规则的坑也提醒我：Makefile 是“目标 + 配方”，只有 `.PHONY` 声明而没有配方时，make 会**安静地什么都不做**。以后每加一条规则，都要用 `make -n <目标>` 先看看它到底会执行什么。
