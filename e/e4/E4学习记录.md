## 二、Verilator 仿真环境

### 1. 安装

我按讲义从 git 安装了 Verilator 的 stable 版本，源码放在 `~/tools/verilator-stable`，没有放进 `ysyx-workbench`，免得框架把工具源码也追踪进去。

安装后检查：

```bash

```

### 2. 怎么驱动电路

Verilator 会把 Verilog 转成 C++。顶层模块叫 `top` 时，生成的类叫 `Vtop`，端口可以通过这个对象读写。C++ 驱动先设置输入，再调用 `eval()`，然后读输出。

```text
Verilog + C++ 驱动 → Verilator 编译 → 可执行程序 → 运行仿真
```

最开始的 npc 目录是这样：

```text
npc/
├── Makefile
├── .gitignore
├── csrc/main.cpp
├── vsrc/
├── constr/top.nxdc
└── build/
```

`vsrc` 放 RTL，`csrc` 放仿真驱动，`constr` 放引脚约束，`build` 放生成的文件。`.gitignore` 按白名单放行源码，编译产物不提交。后来加了 `Makefile.test`，也补了对应的放行规则，否则新写的测试 Makefile 会被忽略。

## 三、双控开关和波形

### 1. 第一个组合电路

双控开关就是两个输入异或：

```verilog
module top(
    input  a,
    input  b,
    output f
);
    assign f = a ^ b;
endmodule
```

输入只有四种组合，我直接在 C++ 里全部试了一遍：

```cpp
for (int a = 0; a <= 1; a++) {
    for (int b = 0; b <= 1; b++) {
        top.a = a;
        top.b = b;
        top.eval();
        printf("a=%d b=%d f=%d\n", a, b, (int)top.f);
        assert(top.f == (a ^ b));
    }
}
```

每次修改输入后都要 `eval()`，再读取 `f`。四组输入对应的输出是 `0、1、1、0`。

### 2. 生成和查看波形

我用 `VerilatedFstC` 生成 `build/wave.fst`，再用 GTKWave 打开。

```cpp
VerilatedFstC trace;
top.trace(&trace, 99);
trace.open("build/wave.fst");

// 每次计算后记录波形，再推进时间
trace.dump(context.time());
context.timeInc(1);
```

刚打开波形时，时间间隔看起来很大，我以为信号没有变化。后来把光标移到四个时间点，逐个读输入输出，才确认结果是对的。Signals 里是可选信号，添加到 Waves 后才显示波形，光标处可以读当前值。


### 2. 引脚怎么接

引脚映射写在 `.nxdc` 中。第一行指定顶层，后面写端口和板卡引脚。双控开关用的是：

```text
top=top

sw (SW1, SW0)
ledr LD0
```

向量列表里第一个引脚对应最高位，所以这里是 `sw[1]` 接 SW1，`sw[0]` 接 SW0。

构建时 `auto_pin_bind.py` 根据约束生成 `auto_bind.cpp`，C++ 驱动再调用绑定函数。需要改接线时修改 `.nxdc`，生成的文件不用手动改。

```cpp
nvboard_bind_all_pins(dut); // 绑定端口
nvboard_init();            // 打开板卡
nvboard_update();          // 读取输入、更新显示
nvboard_quit();            // 退出
```

查了 N4 板卡的引脚名，常用的整理如下：

| 组件 | 引脚 | 对电路的方向 |
|---|---|---|
| 开关 | `SW0`～`SW15` | 输入 |
| 按键 | `BTNC`、`BTNU`、`BTND`、`BTNL`、`BTNR` | 输入 |
| LED | `LD0`～`LD15` | 输出 |
| 数码管 | 各位对应的 A～G 和小数点引脚 | 输出 |
| VGA | 同步、消隐和 RGB 引脚 | 输出 |
| PS/2 | `PS2_CLK`、`PS2_DAT` | 输入 |
| UART | `UART_RX`、`UART_TX` | 输入、输出 |

时钟由 C++ 驱动翻转。复位最开始也由驱动设置，后来有些实验把复位接到了板卡按钮，所以是否写进约束要看实际有没有接板卡输入。

### 3. 双控开关上板

上板时把两个输入改成 `sw[1:0]`，输出接 `ledr`。拨 SW0、SW1，LD0 按异或规律亮灭。

## 五、流水灯

流水灯需要记住当前亮的是哪一位，以及计数器数到了哪里。我先照着参考实现用 `always` 跑通，后来再用两个 `Reg` 改写。

计数器每拍加一，达到 5000000 后归零；当前计数为 0 时，LED 循环左移一位。计数器是为了让换灯慢下来，否则人眼看不到变化。

改写时我把当前值和下一拍的值分开：

| 保存的值 | 下一拍怎么算 |
|---|---|
| `cnt` | 到上限后变成 0，否则加 1 |
| `led` | `cnt==0` 时循环左移，否则保持原值 |

`Reg` 的 `dout` 接当前值，`din` 接组合逻辑算出的下一值。保持不变时可以让 `din` 等于 `dout`，也可以用写使能控制更新。

改完后，我把 `Reg` 版和 `always` 版放到同一个测试顶层，每个上升沿后比较 LED 和计数器。测试把 `CNT_MAX` 改成 4，缩短换灯周期，跑了 1000 万拍，没有差异。对应源码现在保存在 `equiv_light/`，旧流水灯顶层保存在 `npc/examples/`，避免和 sCPU 的 `top` 重名。

## 六、Reg 和 MuxKey

### 1. Reg

后面的时序电路基本都用这个模板保存状态：

```verilog
module Reg #(WIDTH = 1, RESET_VAL = 0) (
    input clk,
    input rst,
    input [WIDTH-1:0] din,
    output reg [WIDTH-1:0] dout,
    input wen
);
    always @(posedge clk) begin
        if (rst)      dout <= RESET_VAL;
        else if (wen) dout <= din;
    end
endmodule
```

| 参数或端口 | 含义 |
|---|---|
| `WIDTH` | 位宽 |
| `RESET_VAL` | 复位后的值 |
| `din`、`dout` | 下一拍输入、当前保存的值 |
| `wen` | 这一拍是否写入 |

模板内部有 `always`，我写模块时只负责实例化和接线。多个寄存器在同一上升沿采样，不能把它们理解成按代码顺序逐个更新。

### 2. MuxKey

`MuxKey` 根据键选择数据。没找到键时输出 0，`MuxKeyWithDefault` 可以另外指定默认值。

```verilog
MuxKey #(2, 1, 1) u_mux (y, s, {
    1'b0, a,
    1'b1, b
});
```

这里 `s=0` 选 a，`s=1` 选 b。三个参数分别是表项数、键宽和数据宽。

我最容易弄混的是 `NR_KEY`。它表示实际写了多少对键值，不是键能表示多少种取值。`lut` 也不是 C 的数组，而是通过 `{}` 拼成的一根宽信号，每一项的顺序是键在前、数据在后。

模板内部把宽信号拆成各个表项，比较键，把匹配项的数据或起来。使用时需要保证键不重复。

## 七、实验二：译码器和编码器

这一部分做了 2-4 译码器、3-8 译码器、4-2 编码器、七段译码器和 8-3 优先编码器，最后把优先编码结果显示到数码管。

| 模块 | 我的写法 |
|---|---|
| `decode24` | 用 `MuxKey` 列出输入和输出 |
| `decode38` | 使能有效时把 `8'b1` 左移 x 位 |
| `encode42` | 独热输入对应编号，用查表选择，其他输入默认输出 0 |
| `bcd` | 查表得到段码 |
| `encode83` | 从高位往低位判断，优先输出最高有效位的编号 |

### 1. 测试里发现的问题

每个模块先单独用 C++ 测，再合起来上板。

`encode42` 的测试循环最开始写成 `x<8`，漏掉了输入 8，而输入 8 应该输出 3。改成 `x<16` 后才把全部输入测到。

2-4 译码器的表里也写错过一项：键 `100` 对应的数据写成了 `0000`，正确值是 `0001`。这个键包含使能和两位输入。

### 2. 数码管极性

我的段码表最开始按高电平点亮来写，上板后显示不对。NVBoard 这里是低电平点亮，输出前加 `~` 才正常。

当时仿真只对照了自己写的表，没有检查板卡极性，所以没发现这个问题。后面做数码管时就先确认哪一位对应哪一段，以及 0 和 1 分别表示亮还是灭。

### 3. 上板结果

| SW7～SW0 | 编码输出 | 有效标志 | 数码管 |
|---|---|---|---|
| `00001110` | 011 | 1 | 3 |
| `10000000` | 111 | 1 | 7 |
| `00000001` | 000 | 1 | 0 |
| `00000000` | 000 | 0 | 0 |

最后两组的编码都是 0，但有效标志不同。当前顶层让数码管始终显示，是否有输入通过独立的 LED 指示。

## 八、实验三：加法器和 ALU

### 1. 从全加器到加减法器

先写一位全加器：

```verilog
assign s = a ^ b ^ cin;
assign cout = (a & b) | (a & cin) | (b & cin);
```

三个输入一共 8 种组合，全部测试通过。再用 `generate for` 把四个全加器接起来，`carry[0]` 是输入进位，`carry[4]` 是最终进位，4 位加法器的 512 种输入也通过了。

减法用 `A + (~B) + 1` 实现。`Sub` 同时控制 B 是否取反，以及输入进位是不是 1：

```verilog
wire [3:0] Bx = B ^ {4{Sub}};
add4 u_add (.a(A), .b(Bx), .cin(Sub), .s(Result), .cout(Carry));
assign Overflow = (A[3] == Bx[3]) && (Result[3] != A[3]);
assign Zero = ~(|Result);
```

溢出判断最开始用的是 `B[3]`，做减法时就错了。加法器实际接的是 `Bx`，判断符号也要用 `Bx[3]`。当时 512 项里有 128 项失败，改完后通过。

### 2. ALU

八种运算分别算出结果，再用 `MuxKey` 按功能码选择。加减法共用前面的模块，比较也通过减法结果得到：

```text
带符号小于：Result[3] ^ Overflow
相等：      ~(|Result)
```

A、B 各有 16 种取值，功能码有 8 种，总共 2048 种组合，测试通过。

这里有两次错误在测试代码里：

- `exp_res =- a & b;` 实际算的是 `(-a) & b`，应改成 `exp_res = a & b;`。
- 初始化 `t_b` 时，else 分支误用了 `t_b` 自己，应该读取 b。

所以出现差异后还得检查期望值，不能默认 RTL 一定错。

### 3. 上板和思考题

SW7～SW4 输入 A，SW3～SW0 输入 B，BTNL、BTNC、BTNR 选择功能，LD3～LD0 显示结果，LD4、LD5、LD6 显示 carry、overflow、zero。八种功能都核对过。原来用上下按钮选功能，后来换成横排三个按钮，比较好按。

减法的 `+1` 放到加法器 Cin 中比较直接。如果先把 `~B+1` 算完并截成 n 位，再做加法，遇到 B 为最小负数时会影响溢出判断。

Zero 写成 `~(|Result)`，意思就是把结果各位或起来，再取反。这里没有做综合后的面积、延迟比较，不能仅凭写法断定它一定比 `Result == 0` 更省硬件。

## 九、实验六：移位寄存器、桶形移位器和 LFSR

### 1. 移位寄存器

移位寄存器用 `Reg` 保存 q，选择器根据控制信号选下一拍的值，包括清零、装载、逻辑左右移、算术右移、串行输入和循环左右移。

我最容易弄反的是位拼接的方向。`{}` 左边是高位，例如：

```text
逻辑左移：{q[6:0], 1'b0}
逻辑右移：{1'b0, q[7:1]}
算术右移：{q[7], q[7:1]}
串行输入：{sin, q[7:1]}
```

先确定哪一位移出去、哪一位补进来，再写拼接，比直接凭左右位置猜更清楚。

### 2. 桶形移位器

8 位桶形移位器拆成三级，分别选择移 1、2、4 位。移位量 `shamt[0]`、`shamt[1]`、`shamt[2]` 控制对应一级。

例如移 5 位，就是经过移 1 位和移 4 位两级，移 2 位那一级保持输入。算术右移补符号位，逻辑右移和左移补 0。当前源码用三元表达式和位拼接写这三级组合逻辑。

### 3. LFSR

我另外做了 8 位 LFSR，复位到 `01`，反馈来自 q 的第 4、3、2、0 位，全 0 时重新回到 `01`：

```verilog
wire fb = q[4] ^ q[3] ^ q[2] ^ q[0];
wire [7:0] nxt = (q == 8'b0) ? 8'h01 : {fb, q[7:1]};
Reg #(8, 8'h01) u_q (.clk(clk), .rst(rst), .din(nxt), .dout(q), .wen(en));
```

第一次测试报了 253 项失败。后来逐拍检查，RTL 的序列是 `01 80 40 20 10 88 c4 e2 ...`，周期为 255；测试中却把 `(cur >> 0)` 写成 `(cur > 0)`，把移位变成了比较。修正后对上了，也补了 255 拍后回到 `01` 的检查。

### 4. 上板

LFSR 全速变化时看不清，我改成按钮步进。顶层保存上一拍的按钮值 `btn_d`，用 `btn & ~btn_d` 检测按下，再接到 LFSR 的使能，时钟仍然由 C++ 驱动产生。

q 的高、低四位分别接一个十六进制数码管。运行后先显示 `01`，每按一次 BTNC，显示沿序列变化：`01→80→40→20→10→88...`。

约束里小数点引脚当时应写 `DEC0P`、`DEC1P`，我猜成 `SEG0P` 后，绑定脚本报了 `Invalid pin SEG0P`。

2026-10-13 同步后发现，目录里的 `main.cpp` 测的是数码管译码器，Makefile 却按 LFSR 的 top 编译，导致找不到 `hex` 和 `seg`。改成测试 `decoder` 后，16 个输入全部通过。这个 16 项结果只对应译码器，上板 LFSR 使用 `Makefile.board`。

## 十、实验七：状态机和 PS/2 键盘

### 1. 模块怎么分

先做连续四个相同输入的状态机练习，再做键盘接收和显示。`fsm.v` 还保留着，当前键盘顶层没有实例化它。

| 文件 | 做什么 |
|---|---|
| `ps2_keyboard.v` | 接收串行帧，检查后存入 FIFO |
| `key_handler.v` | 读取字节，处理按下、重复和松开，保存修饰键状态 |
| `scancode_to_ascii.v` | 把字母、数字扫描码转为基础 ASCII |
| `hex_to_seg.v` | 十六进制数转段码，并控制显示使能 |
| `top.v` | 连线、Shift 转换和显示数据拆分 |
| `main.cpp` | 产生 PS/2 输入并检查输出 |
| `board_main.cpp` | NVBoard 入口 |
| `constr/top.nxdc` | 引脚绑定 |

### 2. 接收帧和 FIFO

PS/2 一帧有 11 位：起始位 0、8 位数据、奇校验位、停止位 1，数据低位先发。接收器检测键盘时钟下降沿后采样，buffer 保存前 10 位，最后一位直接检查。

帧检查通过才写入 FIFO。`ready=1` 表示队首有有效数据，`next_data_n=0` 表示取走这个字节。`next_data_n` 由 `key_handler` 产生，不需要 C++ 再去驱动。

初期试过单字节 `1C`、连续三个字节后按序读取、连续八个字节写入和读回。当前逻辑第八个字节设置 overflow，但八个字节仍能读出；再继续写会覆盖未读数据。overflow 要复位才清除，这个 FIFO 没有在满时阻止写入。

### 3. 按下、长按和松开

| 状态 | 用途 |
|---|---|
| `break_pending` | 收到 F0 后，记住后面的字节是松开键码 |
| `pressed` | 当前字符键是否按住 |
| `keycode` | 保存最近一次新按下的字符键 |
| `press_cnt` | 新按下次数，长按重复不增加 |

以 A 的扫描码 `1C` 为例：

| 收到的字节 | 状态变化 |
|---|---|
| 第一次 `1C` | 保存键码，pressed 置 1，次数加 1 |
| 再次 `1C` | 认为是长按重复，次数不变 |
| `F0` | break_pending 置 1，等待松开键码 |
| 后面的 `1C` | 匹配当前键，pressed 清零 |

松开后键码和次数还保留，只关闭键码和 ASCII 的显示。

我曾把收到 F0 时的 `next_break_pending` 写成 0，结果记不住松开前缀，pressed 一直为 1。64 项测试中有 55 项失败，改成 1 后通过。后面的失败大多是前面状态错了造成的，所以先找第一处不同比较有效。

### 4. ASCII 和显示

基础表包含 26 个字母和 10 个数字，用 `MuxKeyWithDefault` 输出 `{有效标志, ASCII}`，一共 36 项，表外输出 0。

| 数码管 | 内容 |
|---|---|
| 第 1、0 位 | 扫描码 |
| 第 3、2 位 | ASCII |
| 第 5、4 位 | 按键次数 |
| 第 7、6 位 | 不使用，输出 `8'hFF` 熄灭 |

键码和 ASCII 只在 `pressed & ascii_valid` 时显示，次数一直显示。次数是十六进制，09 后面是 0A，增加到 255 后会回到 0。

按下 A 时应显示 `01 61 1C`，松开后只留下次数 01。基础状态测试加上五项显示检查后，共 69 项通过。

未使用的两位数码管通过顶层输出和约束控制熄灭，板卡界面仍保留八位，没有靠删除界面控件来处理。

### 5. Shift 和 Ctrl

左右 Shift、左右 Ctrl 分别保存，使用时把左右两边取或。这样同时按住两个 Shift，松开一个不会把另一个也清掉。修饰键不占用字符键的 pressed，也不增加次数。

| 按键 | 按下 | 松开 |
|---|---|---|
| 左 Shift | `12` | `F0 12` |
| 右 Shift | `59` | `F0 59` |
| 左 Ctrl | `14` | `F0 14` |
| 右 Ctrl | `E0 14` | `E0 F0 14` |

右 Ctrl 松开时，经过 F0 仍然要保留 E0，否则会把扩展键误认成普通键。因此 `extended_pending` 在处理实际键码后才清除。

顶层根据 Shift 状态转换 ASCII，小写字母减 `20h` 变成大写，数字查表转为符号。例如 Shift+A 是 `41`，Shift+1 是 `21`，对应感叹号。字符还按着时松开 Shift，ASCII 会变回小写，次数不增加。

Ctrl 目前只显示按住状态，没有把 Ctrl+A 转成控制字符 01，也没有实现 Caps Lock、多个普通字符键同时按住和全部扩展键。

### 2. 一拍延迟

ROM 是同步读，颜色晚一拍输出，所以 hsync、vsync、valid 也各经过一个 Reg，延迟一拍后再输出。

测试时，计数器和未延迟的地址对当前拍；颜色和延迟后的同步信号对上一拍。最开始模型没有区分这两种情况，就会整体错一拍。

h_addr 和 v_addr 也要分开判断有效区。x 在显示区、y 在消隐区时，水平地址仍按 x 计算，不能因为整体 valid 为 0 就把两个地址都清零。

一整帧是 `800×525=420000` 拍，逐拍测试通过。也分别改错过回绕点、同步极性、有效区边界、地址拼接顺序和延迟，测试都能报错。最后上板图片显示正常，没有偏移或颜色异常。

## 十二、用 RTL 实现 sCPU

### 1. 把 Logisim 电路改成 RTL

这部分沿用 F 阶段的增强版 sISA，运行 `1+2+...+10`，最后用 io 输出到 LED。

| 文件 | 内容 |
|---|---|
| `scpu.v` | PC、译码、数据通路、写回、分支和 io |
| `gpr.v` | 四个 8 位寄存器，用 generate 实例化 Reg |
| `inst_rom.v` | 用 MuxKeyWithDefault 保存程序 |
| `top.v` | 实例化 scpu，把 LED 接到板卡 |
| `test/main.cpp` | 运行程序后检查 PC、寄存器和 LED |

指令格式如下，表中的斜线只用于分隔字段：

| 指令 | 编码字段 | 行为 |
|---|---|---|
| add | `00 / rd / rs1 / rs2` | `R[rd] = R[rs1] + R[rs2]` |
| 增强版 li | `10 / rd / sel / imm2` | `R[rd] = imm2 << (2*sel)` |
| 增强版 bner0 | `11 / offset4 / rs2` | 若 R0 与源寄存器不同，PC 加有符号偏移量 |
| io | `01 / rd / 方向 / idx` | 当前实现把 R[rd] 输出到 LED |

写回数据在立即数和加法结果之间选择，只有 li、add 写 GPR。读口也按指令选择：add 读两个源寄存器，bner0 读 R0 和 rs2，io 读 rd。

LED 单独用一个 Reg 保存，只在 io 输出时更新。直接接 GPR 读口的话，后面读地址变化，LED 也会跟着变。

### 2. 最终结果测试

运行 50 拍后检查：

```text
PC=10，R0=10，R1=10，R2=55，R3=1，LED=55
```

六项检查通过。为了读取内部 GPR，测试包含 `Vscpu___024root.h`，访问 `dut.rootp->scpu__DOT__u_gpr__DOT__regs[i]`。具体名字取决于模块层级，修改 RTL 后可能需要重新查看生成的头文件。

前面的测试还试过七种改错：加法改减法、比较条件反过来、偏移量改成零扩展、PC 每拍加 2、去掉 add 写使能、写回固定选立即数，这六种都被发现。去掉 LED 写使能中的方向判断却仍然通过，因为程序只用了 LED 输出，没有执行输入型 io。

### 3. 写代码时的问题

`io_idx` 曾拼错，分支偏移量也曾多拼两位，变成 10 位后再截断到 8 位，导致跳转不对。还有一次 is_io 的声明和使用位置没整理好，后来一起检查了控制信号的声明和连线。

## 十三、sEMU 和 DiffTest

### 1. 先写 sEMU

sCPU 能算出 55 后，我又用 C++ 写了一个 sEMU。它按同样的指令规则更新变量，不需要搭寄存器和选择器。

状态放在 `CPUState` 中：pc、四个 r 和 led，都是 8 位。程序单独放在数组里。opcode、rd 和立即数是从当前指令拆出的临时值，不需要一直保存。

文件分成了核心和测试入口：

```text
npc/
├── csrc/
│   ├── main.cpp            NVBoard 入口
│   └── semu/
│       ├── semu.h          状态和接口声明
│       └── semu.cpp        程序、复位和单条指令执行
├── test/
│   ├── main.cpp            sCPU 最终结果测试
│   ├── semu_main.cpp       单独运行 sEMU
│   └── difftest.cpp        两边逐条比较
└── Makefile.test
```

sEMU 只提供 `reset()`、`step()` 和 `get_state()`，没有 main。两个测试入口都用这份实现。

### 2. step 怎么写

一次 step 先根据 PC 取指，拆字段，再执行对应指令。next_pc 默认等于当前 PC 加 1，如果需要跳转就改掉它，最后才更新 PC。

add 读取两个旧寄存器值，相加后写回；li 按 sel 移动两位立即数；io 当前只处理输出方向、设备号 0；bner0 比较 R0 和指定寄存器。

跳转需要注意偏移量的符号。地址 8 的 F9 拆开是 `11 1110 01`，其中 `1110` 表示 -2。C++ 取出来是 14，最高位为 1 时减去 16，就得到 -2。

```text
R0 != R1：下一 PC = 8 - 2 = 6
R0 == R1：下一 PC = 9
```

这里用的是当前 PC。如果先更新 PC，再算偏移，就会多加 1。

独立测试执行 50 条指令，检查 PC、四个寄存器和 LED，得到 `PASS: 6`，结果与 sCPU 一样。

### 3. 接入 DiffTest

最终结果一样，还不知道中间每条指令是否正确，所以把两边放进同一个驱动逐条比较。

当前 sCPU 一拍执行一条指令，sEMU 一次 step 执行一条。两边先复位，每次循环按这个顺序做：

```text
保存执行前 PC 和指令
→ tick(dut)
→ ref.step()
→ 比较执行后的 PC、R0～R3 和 LED
```

比较放在两边都执行之后。50 条指令，每条检查六项，输出 `PASS: 300`。

测试直接用 `--top-module scpu`，这样可以读 dut.pc 和 dut.inst。top.v 只是上板时用的外层连接，不需要放进这个测试。内部 GPR 用 `--public-flat-rw` 保留后读取。

### 4. 报错信息和 PC 检查

我沿用之前测试里的 fails、total，分别统计失败项和总项数。某条指令出现差异时，先打印这一条的全部差异，再停止。

报错里保存的是执行前 PC 和机器码。因为 tick 之后 PC 已经更新了，直接打印 dut.pc，看到的是下一条指令地址。

PC 也要比较。bner0 不写 GPR，只比较寄存器的话，跳错时可能还看不出差异。

### 5. 故意改错试一下

第一轮只修改 RTL 的加法，让结果多加 1，sEMU 不改。测试输出：

```text
r0=11 (expect r0=10)
step=3: pc=02 inst=01
FAILED: 1/18
```

第三条指令是 R0 加 R1，执行前分别为 8 和 2，正确结果是 10，改错后变成 11，所以第三条就停了。三条指令共检查 18 项，一项失败。

恢复加法后，再让 branch_target 多加 1，结果是：

```text
pc=7 (expect pc=6)
step=9: pc=08 inst=f9
FAILED: 1/54
```

第九条第一次执行 F9，正确目标为 6，改错后跳到 7，PC 检查当场发现。这里报错中的 08 是跳转指令地址，7 和 6 是执行后的实际 PC、期望 PC。

当时输出里还把 FAILED 写成了 FALIED，cycle 也误用了寄存器编号，后来改了打印代码。测试失败时返回 1，make 跟着报 Error 1，是这次改错测试的预期结果。

两轮都恢复后重新编译，sEMU 和 DiffTest 再次输出 `PASS: 6`、`PASS: 300`。
