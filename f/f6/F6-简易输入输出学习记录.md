# F6：简易输入输出学习记录

## 1. 阶段目标

本阶段在已经支持增强版 `li`、`add` 和 `bner0` 的 `sCPU_enhanced` 上加入简易 I/O，使程序能够：

- 把 GPR 中的数据输出到 8 位 LED；
- 把 GPR 中的数据输出到两个十六进制数码管；
- 从 8 位拨码开关读取数据并写入指定 GPR；
- 为按钮输入设备预留统一的输入设备选择通路。

本阶段最终验证了 LED、十六进制数码管和拨码开关。按钮输入的数据通路设计已经明确，但当前保存的电路尚未实例化完整的 8 个按钮；“单步求和”程序没有继续实现，不计入本阶段成果。

## 2. `io` 指令格式

```text
 7  6 | 5  4 |  3  | 2  1  0
------+------+-----+---------
 0  1 |  rd  | i/o |   idx
```

字段含义：

```text
opcode[7:6] = 01：io指令
rd[5:4]          ：读出或写入的GPR编号
i/o[3] = 0       ：从设备输入到R[rd]
i/o[3] = 1       ：把R[rd]输出到设备
idx[2:0]         ：设备编号
```

输入和输出拥有独立的方向，因此可以复用相同的设备编号：

| `i/o` | `idx` | 设备 |
|---:|---:|---|
| 0 | `000` | 8 位拨码开关 |
| 0 | `001` | 8 个按钮（扩展方案） |
| 1 | `000` | 8 位 LED Bar |
| 1 | `001` | 两个 Hex Digit Display |

常用机器码：

```text
0x40 = io输入：拨码开关 → R0
0x41 = io输入：按钮 → R0
0x68 = io输出：R2 → LED
0x69 = io输出：R2 → 十六进制数码管
```

## 3. `io` 指令译码

原来的 2-to-4 opcode Decoder 已经有一个空闲输出：

```text
Decoder.output0 → is_add
Decoder.output1 → is_io
Decoder.output2 → is_li
Decoder.output3 → is_bner
```

另外从 8 位指令中拆出：

```text
instruction[3]   → io_direction
instruction[2:0] → idx
```

设备编号使用一个 3-to-8 Decoder 统一译码：

```text
idx[2:0] → 3-to-8 Decoder.Select

Decoder.output0 → device_0
Decoder.output1 → device_1
```

同一根设备选择信号在不同方向下具有不同含义：

```text
device_0 + 输入方向 → Dip Switch
device_0 + 输出方向 → LED

device_1 + 输入方向 → Buttons
device_1 + 输出方向 → Hex Display
```

## 4. 输出数据通路

### 4.1 用 `rd` 读取输出数据

输出型 `io` 需要读取 `R[rd]`。为了复用现有 GPR 读端口，在原 `rdata2` 四选一 MUX 的 Select 前增加一个 2 位二选一 MUX：

```text
input0 ← rs2
input1 ← rd
Select ← is_io
输出   → 原rdata2四选一MUX.Select
```

因此：

```text
普通指令：rdata2 = R[rs2]
io指令：  rdata2 = R[rd]
```

原四选一 MUX 的 `R0.Q～R3.Q` 数据输入保持不变，只修改它的读地址来源。

### 4.2 LED 输出

LED 写使能为：

```text
LEDWrite = is_io AND io_direction AND device_0
```

增加独立的 8 位输出寄存器 `LED_Data`：

```text
LED_Data.D   ← rdata2
LED_Data.WE  ← LEDWrite
LED_Data.CLK ← CPU公共clk
LED_Data.R   ← CPU公共rst
LED_Data.Q   → 8位LED Bar
```

独立输出寄存器用于保持设备状态。若把 LED 直接连接到 `rdata2`，后续指令改变 GPR 读地址时，LED 也会随组合信号变化。

测试指令：

```text
0x68 = 01 10 1 000 = io LED,r2
```

当求和结果为 `R2=0x37` 时，执行一次 `0x68` 后：

```text
LED_Data = 0x37
LED Bar  = 00110111
```

程序只在最后执行一次 `io` 时，LED 才从全黑变成最终结果。这是正确行为，因为求和期间的 `add` 只修改 R2，不修改 `LED_Data`。

### 4.3 十六进制数码管输出

数码管写使能为：

```text
HEXWrite = is_io AND io_direction AND device_1
```

增加独立的 8 位输出寄存器 `HEX_Data`：

```text
HEX_Data.D   ← rdata2
HEX_Data.WE  ← HEXWrite
HEX_Data.CLK ← CPU公共clk
HEX_Data.R   ← CPU公共rst
```

`HEX_Data.Q` 通过 Splitter 拆成两个 4 位信号：

```text
HEX_Data[7:4] → 左侧Hex Digit Display
HEX_Data[3:0] → 右侧Hex Digit Display
```

两个显示器均设置：

```text
Has Decimal Point = No
```

测试指令：

```text
0x69 = 01 10 1 001 = io HEX,r2
```

求和结果为 `R2=0x37` 时，执行后显示：

```text
左侧数码管：3
右侧数码管：7
```

这里的 `37` 是十六进制，对应十进制 `55`。

## 5. 输入数据通路

### 5.1 拨码开关组成 8 位输入

Dip Switch 设置：

```text
Number of Switch = 8
```

该组件不是直接提供一条现成的 8 位总线，而是提供 8 个独立的 1 位输出。使用 Splitter 反向合并：

```text
Switch0 → bit0
Switch1 → bit1
...
Switch7 → bit7

Splitter粗线端 → switch_data[7:0]
```

在 `switch_data` 上添加十六进制 Probe。逐位验证：

```text
bit0 = 1 → 01
bit1 = 1 → 02
bit3 = 1 → 08
bit3和bit1同时为1 → 0A
```

### 5.2 输入设备选择

当只有拨码开关时，`switch_data` 可以直接送入 I/O 写回 MUX。扩展按钮后，应增加输入设备 MUX：

```text
input0 ← switch_data
input1 ← button_data
Select ← device_1
输出   → io_input_data
```

于是：

```text
idx=000 → io_input_data=switch_data
idx=001 → io_input_data=button_data
```

按钮和拨码开关使用同一套 GPR 写回机制，不需要分别建立写回通路。

### 5.3 写回 GPR

输入型 `io` 的控制信号：

```text
IOInputWrite = is_io AND NOT(io_direction)
```

在原有 ALU/立即数 WriteBack 输出与 GPR 数据总线之间增加最终 8 位二选一 MUX：

```text
input0 ← 原WriteBack结果
input1 ← io_input_data
Select ← IOInputWrite
输出   → wdata → R0.D、R1.D、R2.D、R3.D
```

GPR 全局写使能扩展为：

```text
RegWrite = is_add OR is_li OR IOInputWrite
```

各寄存器仍由 `rd` Decoder 独热选中：

```text
R0.WE = RegWrite AND RD0
R1.WE = RegWrite AND RD1
R2.WE = RegWrite AND RD2
R3.WE = RegWrite AND RD3
```

输出型 `io` 不应写 GPR，因此不能简单写成：

```text
RegWrite = is_add OR is_li OR is_io
```

### 5.4 拨码开关输入测试

拨码开关设为 `0x0A`，ROM 地址0使用：

```text
0x40 = 01 00 0 000 = io输入：Dip Switch → R0
```

时钟上升沿之前：

```text
instruction  = 40
is_io        = 1
io_direction = 0
idx          = 000
switch_data  = 0A
IOInputWrite = 1
wdata        = 0A
R0.D         = 0A
R0.WE        = 1
```

产生一次上升沿后：

```text
R0.Q = 0A
```

之后改变拨码开关不会立即改变 R0；只有再次执行输入型 `io` 时才重新采样。

## 6. 使用拨码开关决定求和末项

验证程序使用以下指令序列：

| 地址 | 机器码 | 作用 |
|---:|---:|---|
| 0 | `40` | 从拨码开关读取末项到 R0 |
| 1 | `B1` | `li r3,1` |
| 2 | `17` | `R1=R1+R3` |
| 3 | `29` | `R2=R2+R1` |
| 4 | `F9` | R0 与 R1 不等时相对跳回地址2 |
| 5 | `69` | 把 R2 输出到十六进制数码管 |
| 6 | `00` | 未使用 |
| 7 | `00` | 未使用 |

拨码开关设为 `0x0A` 时，最终结果：

```text
R0 = 0A
R1 = 0A
R2 = 37
数码管显示 = 37
```

若末项输入为 `0`，程序不会立即得到空和0。循环先执行 `R1=R1+1`，随后才比较；R1 会从 `00` 经过 `01～FF`，溢出回 `00` 后才退出。8 位累加结果最终为：

```text
1+2+...+255 ≡ 0x80 (mod 256)
```

题目不要求修复这一边界情况。

## 7. 按钮输入的扩展认识

8 个 Button 同样可以通过 Splitter 合并为 `button_data[7:0]`：

```text
按下 → 对应位为1
释放 → 对应位为0
```

测试按钮输入到 R0 的机器码为：

```text
0x41 = 01 00 0 001
```

按钮是瞬时电平输入。只有在执行 `io` 的有效时钟沿保持按下，对应的1才会写入 GPR；释放后 `button_data` 立即回到0，但已经写入的 GPR 会保持原值。

持续按住按钮时，轮询程序会在每次读取时都得到1，所以可能连续推进。若要实现“一次按下并释放只触发一次”，软件必须分别等待：

```text
等待0→1：确认按下
等待1→0：确认释放
```

本阶段没有继续实现该单步求和程序。

## 8. BUG 调试记录与解决

### 8.1 `is_io` 没有连接到 GPR 读地址 MUX 的 Select

现象：

```text
not_equal输出异常，io读取的rdata2也不正确
```

原因：新增的 `rs2/rd` 二选一地址 MUX 的 Select 悬空，导致 `rdata2` 的读地址不确定。

修复：

```text
is_io → 地址MUX.Select
input0=rs2
input1=rd
```

修复后，普通指令继续读取 `R[rs2]`，`io` 正确读取 `R[rd]`，`not_equal` 也恢复正常。

### 8.2 数码管始终显示 `00`

现象：LED 已显示 `37`，但数码管仍显示 `00`。

先后发现的问题：

1. `is_HEX` 错接到了设备 Decoder 的 output2，实际应该接 output1；
2. ROM 仍使用 `0x68`，执行的是 LED 输出，而不是数码管输出；
3. `HEX_Data.Q` 到 8 位 Splitter 的主干以及两个4位分支曾未正确接通。

修复：

```text
Decoder.output1 → is_HEX
ROM输出指令：68 → 69
HEX_Data.Q → Splitter粗线端
[7:4] → 左数码管
[3:0] → 右数码管
```

修复后显示 `37`。

### 8.3 Splitter 位分配遗漏或左右接反

现象：数码管显示错误、缺位或显示成 `73`。

排查方法：分别观察两个4位分支：

```text
HEX_Data=37时：
高4位必须为3
低4位必须为7
```

若显示 `73`，交换两个显示器输入；若出现位宽错误，则检查 bit0～bit7 是否全部分配到两个4位分支，不能漏掉某一位。

### 8.4 误以为 Dip Switch 直接提供8位输出

现象：找不到所谓的单一输出端口。

原因：8位 Dip Switch 提供的是8个独立1位输出。

修复：使用 Splitter 反向合并为 `switch_data[7:0]`，并用 Probe 逐位验证 `01、02、04、08、...、80`。

### 8.5 `switch_data=0A`，但 `R0.Q=08`

现象：拨码开关总线已经为 `0A`，但 `IOInputWrite=0`、`wdata=08`，R0仍写入08。

原因：ROM 地址0仍是旧的 `0x86`，CPU执行的是增强版 `li`，不是拨码输入指令。此时 `IOInputWrite=0` 和 `wdata=08` 都是旧指令的正确结果。

修复：

```text
ROM地址0：86 → 40
```

复位并重新执行后：

```text
IOInputWrite=1
wdata=0A
时钟后R0.Q=0A
```

这说明排查时必须先确认当前 PC 和 instruction，不能只根据期望指令判断控制信号。

## 9. 阶段总结

本阶段完成了一个按方向位和设备编号统一寻址的简易 I/O 系统：

```text
io输出：GPR读端口 → 独立设备数据寄存器 → LED/数码管
io输入：外部输入设备 → 输入设备MUX → GPR写回MUX → R[rd]
```

关键认识：

- `idx` 只选择设备，`i/o` 决定访问方向；同一个编号可以分别代表输入和输出设备；
- 输出设备需要数据寄存器保持状态，输入设备由用户控制，不需要额外暂存寄存器；
- 多个输入设备复用同一套 GPR 写回，只需在写回前选择输入数据来源；
- 组合信号必须在时钟沿前正确，寄存器状态只能在有效时钟沿更新；
- 调试顺序应为 `instruction → 控制信号 → MUX选择 → D/WE → 时钟后Q`。
